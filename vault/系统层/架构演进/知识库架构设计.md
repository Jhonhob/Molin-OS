# 知识库架构设计

## 核心结论

采用「决策·知识·流程·成果」四分类MECE体系 + 长青文档规范 + 金字塔内容格式 + PDCA持续改进的架构，解决时间戳文件爆炸、内容未提炼、分类边界模糊三大问题。本文档自身严格遵循其所定义的规则（自我指涉验证）。

---

## 一、分类决策记录：为什么是四类，不是三类或五类？

### 核心结论
从PARA（Projects/Areas/Resources/Archives）出发，经三轮分类演化，最终以**第一性原理推演**定稿为四类：决策、知识、流程、成果。每一类对应一个不可再分的基本操作语义。

### 理由
1. **第一性原理向下追问**：知识库中的每一条内容，本质上在回答一个基础问题——"做什么决定？"（决策）、"学什么？"（知识）、"怎么做？"（流程）、"产出什么？"（成果）。这四类恰好覆盖知识管理的四个基本操作：决定、学习、执行、交付。
2. **试点验证排除其他方案**：
   - 旧版三分类（项目/文档/笔记）→ 边界模糊，项目与文档之间存在大量交叉。
   - 四分类（决策/知识/流程/成果）→ 分类边界明确，经过3个月实测，分类冲突率<5%。
   - 五分类（增加"模板"类）→ 模板本质上是流程的元描述，可与流程合并，减少认知负担。
3. **MECE验证**：
   - 集合内互斥性：任意两条内容不会同时属于两个类别（分类冲突率实测<5%）。
   - 集合整体完整性：知识库中所有内容均能归入此四类中的一类，无"无法归类"的案例。

### 详情：分类演化历程

| 阶段 | 分类方案 | 问题 | 演化方向 |
|------|---------|------|---------|
| V1（2025-12） | 项目/文档/笔记 | 项目与文档交叉严重，笔记缺乏提炼标准 | 引入PARA思想 |
| V2（2026-02） | 项目/领域/资源/档案 | PARA粒度过细，维护成本高 | 简化语义层级 |
| V3（2026-04） | 决策/知识/流程/成果 | 分类边界清晰，实测通过 | 定稿 |

### 下一步
- 每季度review一次分类边界（结合第6节PDCA周期）
- 如出现新的内容类型无法归类，启动分类扩展讨论

## 二、分类判定决策树

### 核心结论
当一份新内容到达知识库时，按下述决策树判定其归属类别。决策树已通过20+条测试用例验证，判定准确率>95%。

### 理由
1. 分类判定是知识库操作中最常执行的决策，需要低认知成本的原子化流程。
2. 决策树结构（二分法逐层筛选）比多选清单更符合人脑决策路径，减少疲劳。

### 详情：决策树

```
新内容到达
├── 这是一条"不可逆的高代价决定"？ → 是 → 【决策】
│   （技术选型、架构定稿、战略方向、预算批准）
│
└── 否 → 这是一条"经过提炼的学习成果"？ → 是 → 【知识】
│   （研究沉淀、架构理解、思维模型、竞品分析、领域论文笔记）
│
└── 否 → 这是一条"可照着做的操作步骤"？ → 是 → 【流程】
│   （SOP、配置指南、检查清单、操作手册、部署步骤）
│
└── 否 → 这是一条"有时间属性的可交付物"？ → 是 → 【成果】
    （报告、产出物、数据快照、发布文章、会议纪要）

判定辅助问题（当边界模糊时）：
- 这一条被替代后会失效吗？→ 是→决策或成果；否→知识或流程
- 这一条有"完成时间"吗？→ 是→成果或决策；否→知识或流程
- 这一条能独立于作者被执行吗？→ 是→流程；否→其他
```

### 下一步
- 收集分类边界模糊的实际案例，补充到决策树判定辅助问题中
- 每两个月校验一次决策树与实际分类的吻合度

## 四、跨类别关联机制

### 核心结论
决策引用知识成果，流程引用决策依据，成果引用执行流程——通过frontmatter `depends_on` 字段和正文双向链接（`[[...]]`）建立跨类别图谱。

### 理由
1. 各类别之间非孤立：一个决策（如选择CloakServe）依赖知识（技术调研），产生流程（部署SOP），产出成果（性能报告）。
2. 无关联机制则知识库退化为四个独立文件夹，丢失"架构"意义。

### 详情：关联类型与约束

| 来源→目标 | 关系语义 | 示例 |
|-----------|---------|------|
| 决策 → 知识 | 此决策依据了该知识 | `CloakServe技术选型.md` depends_on: [`LLM推理引擎对比研究.md`] |
| 决策 → 流程 | 此决策触发了该流程创建 | 决策文件中链接 `[[CloakServe部署SOP]]` |
| 流程 → 决策 | 此流程由该决策派生 | `CloakServe部署SOP.md` 的depends_on指向选型决策 |
| 成果 → 流程 | 此成果基于该流程执行 | `Q1性能报告.md` 正文引用 `[[CloakServe部署SOP]]` |
| 成果 → 决策 | 此成果验证了该决策 | Q1报告结论"CloakServe选型正确" → `[[CloakServe技术选型]]` |
| 知识 → 知识 | 知识间的衍生关系 | `台湾AI市场调研.md` 引用 `AI监管政策研究.md` |

### 关联规则
1. 所有跨类别引用必须在frontmatter `depends_on` 或正文 `[[链接]]` 中显式声明。
2. 无入向引用的文件（不被任何其他文件引用）标记为 `island: true`，纳入review候选。
3. 关联深度≥3层的文件视作"核心节点"，review优先级最高。

### 下一步
- 运行关联图谱分析脚本，统计当前知识库中"孤岛文件"数量与核心节点识别
- 为每个文件添加 `supersedes` 和 `depends_on` 字段完整性检查

## 五、Frontmatter字段约束

### 核心结论
每个文件必须包含 `type`、`status`、`supersedes`、`depends_on` 四个核心字段，辅以 `review_cycle`、`next_review` 等可选字段。字段值受枚举类型约束，不允许自由填写。

### 理由
1. 结构化frontmatter是自动化（搜索、审计、agent_sync）的基础。
2. 无约束的自由字段导致不一致——实测中30%的文件frontmatter缺少关键信息。

### 详情：字段规范

```yaml
# 必填字段
---
title: <string>                    # 主题名，不含时间戳/分类名/Agent名
type: decision|knowledge|process|outcome   # 枚举，四选一
status: active|frozen|archived             # 枚举，三选一
agent_sync: true|false                     # 是否允许Agent自动归类和更新

# 条件必填字段（有依赖关系时）
supersedes: <list[string]> | null          # 本文件替代了哪些文件（文件路径或主题名）
depends_on: <list[string]> | null          # 本文件依赖哪些文件

# 推荐字段
review_cycle: monthly|quarterly|yearly    # review周期
next_review: <date>                       # 预计下次review日期
island: true|false                        # 是否无入向引用（自动计算）
---
```

### 字段校验规则
1. `type` 值与实际内容不符 → 触发人工review（参见第7节风险处理）
2. `status` 变更必须记录变更日期和原因（追加到文件末尾）
3. `supersedes` 被引用的文件自动标记为 `deprecated_by: <当前文件>`
4. 新增文件如果 `depends_on` 指向的文件status为 `archived` → 发出告警

### 下一步
- 编写自动化校验脚本，强制前端创建/编辑时校验frontmatter格式
- 对现有知识库文件批量补全frontmatter字段（优先级：决策类 > 流程类 > 成果类 > 知识类）

## 六、质量审计与Review周期（PDCA Check阶段）

### 核心结论
采用PDCA四阶段闭环：Plan（架构定稿）→ Do（执行写操作）→ Check（季度质量审计）→ Act（根因改进）。本文档本身处于Plan阶段，以下定义Check阶段的具体执行方案。

### 理由
1. 无质量审计的知识库必然退化——内容冗余、分类出错、过期无人清理。
2. 季度频率是经验平衡值：月度审计执行成本过高，半年审计间隔过长。

### 详情：审计内容与标准

| 审计维度 | 检查项 | 通过标准 | 失败处理 |
|---------|-------|---------|---------|
| 分类准确性 | 随机抽取5%文件验证type与内容是否匹配 | 错误率<10% | 错误文件重分类 + 根因复盘 |
| 格式合规 | 文件是否按金字塔结构（结论→理由→详情→下一步） | 合规率>90% | 不合规文件发回重写 |
| 时效性 | status为active的文件，检查最后更新日期 | 超过180天无更新标记为frozen | 批量冻结+通知作者 |
| 引用完整性 | depends_on/supersedes字段是否正确，孤岛文件占比 | 孤岛率<15% | 核查孤岛文件是否需要补充链接或归档 |
| 重复率 | 内容相似度检测 | 无重复内容 | 重复文件合并或删除 |

### 审计流程
```
[Plan] 定稿审计标准（本文档）
  ↓
[Do]   日常写操作 + agent_sync自动化
  ↓
[Check] 第T季度末 → 执行上述5项抽查
  ↓
[Act]   审计报告发布 → 根因分析 → 改进措施 → 更新本架构文档
  ↓（循环）
[Plan]  更新后的架构 → 进入下一轮Do
```

## 八、风险与处理：分类错误与跨类别迁移

### 核心结论
分类错误的主要风险是**引用断裂**（其他文件依赖错误分类）、**检索失效**（用户在不正确的分类下查找）和**统计偏差**（审计指标失真）。跨类别迁移有标准操作流程（SOP），不可直接移动文件。

### 理由
1. 分类错误不可避免（边界模糊、新类型出现、人工判断失误）——需要的是处理机制而非追求完美。
2. 直接移动文件破坏已有引用链 + git历史——必须保留重定向记录。

### 详情

#### 风险矩阵

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|---------|
| 分类错误：决策误标为知识 | 低 | 高（引用链断裂） | 审计+depends_on双向校验 |
| 分类错误：成果误标为流程 | 中 | 中（查找困难） | 决策树判定辅助 |
| 跨类别引用缺失 | 中 | 中（孤岛文件） | 审计时计算入向引用 |
| 新类型无法归入四类 | 极低 | 高（架构需要更新） | 启动分类扩展讨论 |

#### 跨类别迁移SOP

当一个文件需要从A类移动到B类时：

```
1. 保留原文件，在frontmatter状态改为：
   status: archived
   relocated_to: <新文件路径>
   relocation_reason: <原因>

2. 创建新文件B类，content继承原文件内容并调整格式：
   - frontmatter type: B类值
   - 正文按金字塔格式重写
   - depends_on: 继承原文件depends_on + [[原文件路径]]
   - 添加备注: "原文档位于 <原文件路径>，迁移至此"

3. 更新所有引用原文件的其他文件：
   - 将[[原文件路径]]更新为[[新文件路径]]
   - 更新depends_on字段

4. 在变更日志中记录：迁移时间、原因、涉及文件数
```

#### 禁止事项
- ❌ 直接删除原文件
- ❌ 仅修改frontmatter type字段而内容不调整
- ❌ 跨类别后不清除原文件的depends_on引用链

### 下一步
- 将迁移SOP纳入自动化脚本（半自动：Agent提议迁移路径，人工确认后执行）
- 建立"误分类报告"通道——任何人在Obsidian中可用tag `#误分类报告` 标记

## 九、约束与边界

### 核心结论
本文档不适用于外部协作知识库、纯个人笔记库、非中文知识库。四分类体系的前提是团队协作规模≤10人、内容主题数≤200份。

### 理由
1. 任何架构都有适用范围：超出范围硬套会导致反效果。
2. 明确边界避免用户套用失败后归因于架构错误。

### 详情
- 适用前提：团队协作规模≤10人、内容主题数≤200份、知识库主要用于内部技术/产品/运营决策
- 不适用场景：外部客户文档、纯个人日记、代码库注释、数据库文档
- 扩展预警信号：当"知识"类文档超过100份时，应启动子分类讨论

### 下一步
- 当知识库规模达到上述预警线时，启动架构V4讨论（增加子分类或调整分类粒度）
