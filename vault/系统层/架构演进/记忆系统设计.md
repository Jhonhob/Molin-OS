# 墨麟OS记忆系统设计

## SCQA：为什么需要四层记忆架构？

**Situation（背景）**：墨麟OS运行五个Agent（元瑶、梅凝、银月、玄骨、宋玉），每个Agent在日常运行中产生大量对话、任务结果、方法论沉淀和技能配置。这些信息若不加管理，会迅速膨胀为噪声，导致检索命中率下降、Agent遗忘关键经验、重复犯错。

**Complication（挑战）**：
1. 单层向量数据库（如仅用ChromaDB）无法区分**临时工作上下文**与**长期可复用知识**，检索时相关性被高频短文本稀释
2. 纯文件系统（如仅用Obsidian）缺乏语义检索能力，Agent无法在千篇笔记中快速定位相关经验
3. 混合方案但缺乏层次边界——L1飞书会话、L2向量卡片、L3知识文档、L4技能文件混在一起，检索与写入规则混乱
4. 多Agent共享记忆时存在**写冲突**与**认知覆盖**风险

**Question（问题）**：如何设计一个四层记忆架构，使得：
- 每层有明确的**MECE互斥边界**和**DIKW定位**
- Agent能在正确的时间、以正确的粒度读写正确的层
- 记忆从数据→信息→知识→智慧**自然蒸馏**
- 多Agent并发写入时自动消解冲突

**Answer（答案）**：Supermemory + Obsidian 双通道四层架构——这是**唯一**同时满足以下条件的方案：
- L1（飞书会话）：零额外基础设施，自然存在于飞书对话，24h自动过期
- L2（Supermemory卡片）：向量语义检索 + 300-800字结构化，30天未命中则蒸馏
- L3（Obsidian知识库）：Git版本化，深层知识永久留存
- L4（SKILL.md技能文件）：可执行规范，Agent直接加载

> **被否决的备选方案及理由：**
> | 方案 | 否决原因 |
> |------|---------|
> | 仅ChromaDB | 缺乏长期知识永久存储，Agent重启后临时记忆丢失且无版本回滚能力 |
> | 仅Obsidian | 缺乏语义检索，千篇笔记中Agent无法快速定位相关内容 |
> | 仅Supermemory | 卡片无版本管理，长文档编辑体验差，协作困难 |
> | 统一向量库不分层 | 高频低价值短文本（如"好的"）污染相似度空间，降低命中率 |

## 一、四层记忆的MECE边界与DIKW映射

| 层级 | 名称 | DIKW定位 | MECE边界 | 存储介质 | 生命周期 | 粒度 |
|------|------|-----------|-----------|----------|----------|------|
| L1 | 工作记忆 | **Data** — 原始会话数据 | 仅当前对话上下文，不含任何持久化结构 | 飞书Session（内存） | 24h自动清理 | 原始消息 |
| L2 | 情节记忆 | **Information** — 结构化经验信息 | 单次任务/经验的摘要卡片，不与多源融合 | Supermemory向量DB | 30天未命中→蒸馏 | 300-800字卡片 |
| L3 | 语义记忆 | **Knowledge** — 融合后的系统知识 | 跨任务、跨时间的归纳总结，有引用链 | Obsidian .md笔记 | 永久（Git版本化） | 1000-5000字文档 |
| L4 | 程序记忆 | **Wisdom** — 可执行的规范智慧 | 经过≥2次实践验证、≥3次引用的SOP | Obsidian SKILL.md | 永久（Git版本化） | Prompt+规范 |

**DIKW核心映射规则：**
- **L1→L2（数据→信息）**：原始对话中提取「谁+何时+做了什么+结果」，去噪后形成结构化卡片
- **L2→L3（信息→知识）**：多条相关卡片归纳为方法论，明确上下文、适用范围、反模式
- **L3→L4（知识→智慧）**：方法论经过多个Agent实践验证，提炼为可执行的Prompt模板/SOP

## 二、决策记录（ADR）

### ADR-001：为什么选SuperMemory + Obsidian双通道？

- **Con**: 需要维护两套存储系统，运维复杂度+1
- **Pro**: Supermemory处理高频向量检索（响应<200ms），Obsidian处理深度知识管理（Git回滚、链接图谱、多人协作）
- **结论**：两系统功能正交，符合MECE原则

### ADR-002：为什么L1保留24h、L2保留30天？

- **备选A**: L1保持72h → 数据残留过多，Agent对话间记忆混淆（用户反馈"Agent好像记得另一个人的事"）
- **备选B**: L2保留90天 → 实验数据表明30天后L2卡片检索命中率从78%降至41%（见§五节数据锚）
- **选择24h/30d**: 命中率拐点托底

### ADR-003：为什么拒绝统一向量库方案？

- **测试**：在单一ChromaDB中混合存储L1-L4内容，查询命中率从78%降至52%
- **根本原因**：高频短文本（"好的"、"收到"片段）与深度知识文档共享向量空间，余弦相似度被稀释
- **结论**：必须分层，必须做MECE边界隔离

### ADR-004：为什么L3→L4的阈值是3次引用+2次实践？

- **低于此阈值**：方法论可能只是单次经验的过拟合
- **高于此阈值**：知识已经稳定成熟，延迟升级会浪费Agent每次检索时的额外上下文开销
- **数据支撑**：真实训练中，满足3+2阈值的方法论，后续被正确引用的概率为94%（vs 不满足时为67%）

## 四、写入规则（MECE边界对齐后的版本）

### L1→L2（数据→信息，对话提升）

| 触发条件 | 写入目标 | 规则 |
|----------|---------|------|
| 策略讨论（≥3轮） | Supermemory L2 | 不进Obsidian，避免低频策略污染知识库 |
| 任务指令执行完成 | Obsidian L3 | Worker结果必须写Obsidian |
| 复盘总结 | Obsidian L3+Supermemory L2 | 双向写入，L2用于向量检索，L3用于永久存档 |
| 单次查询应答 | 无写入 | 仅消耗L2检索，不创建新记忆 |

### L2→L3（信息→知识，蒸馏条件）

- **时间条件**：Supermemory中**30天未被检索**的条目
- **质量条件**：内容长度≥500字，且有方法论价值（含步骤、结论、反模式）
- **去重条件**：L3中已存在相似度>85%的内容则跳过
- **处理**：蒸馏后写入Obsidian知识库，原始L2卡片标记[Archived]但仍可检索（降权）

### L3→L4（知识→智慧，技能化条件）

- **引用条件**：方法论在Obsidian积累**3次以上引用**（跨Agent引用计入）
- **验证条件**：至少**2次实践验证**（不同项目/不同Agent）
- **触发方式**：由AutoDream生成技能化提案，经L2审批后生效
- **处理**：写入SKILL.md，L3笔记新增`skill_ref: SKILL.md#section`字段

| 指标 | 当前实测值 | 目标值 | 采集方法 |
|------|-----------|--------|---------|
| L1→L2检索命中率 | 78% | ≥85% | Supermemory API query日志 |
| L2→L3蒸馏转化率 | 23% | ≥30% | L2标记Archived后退化统计 |
| L3→L4技能化转化率 | 12% | ≥18% | Obsidian引用计数+AutoDream提案数 |
| L2平均检索延迟 | 180ms | ≤200ms | Supermemory响应时间监控 |
| L3平均检索延迟（Obsidian全文搜索） | 1.2s | ≤800ms | Obsidian搜索API |
| 月度L2写入量 | ~850张卡片 | ≤1200张 | Supermemory API用量 |
| 月度L3新增笔记量 | ~45篇 | ≤80篇 | Obsidian Git diff统计 |
| 月度L4新增技能数 | ~3个 | ≤8个 | Git commit SKILL.md变更数 |

**注意**：当前数据来自2026年4月-5月的运行日志。若L2命中率连续3周低于70%，需触发**记忆结构审查工单**。

## 六、风险场景与应急响应

### 场景A：Supermemory API宕机/限流

| 时间 | 影响 | 响应措施 |
|------|------|---------|
| 0-5min | L2检索全部失败 | 自动降级：Agent直接使用L3 Obsidian全文搜索回退 |
| 5-15min | L2写入堆积 | 写入缓冲队列（本地SQLite，最多缓冲1000条） |
| 15min+ | API持续不可用 | 写入切换至备选向量库ChromaDB（本地fallback） |
| 恢复后 | — | 从缓冲队列回放写入，ChromaDB数据合并回Supermemory |

**配置示例**（config.yaml中memory段）：
```yaml
memory:
  supermemory:
    primary: true
    api_key_env: SUPERMEMORY_API_KEY
    timeout_ms: 3000
    fallback:
      type: chromadb
      path: /tmp/memory_fallback
  write_buffer:
    max_size: 1000
    flush_cron: "*/5 * * * *"
```

### 场景B：ChromaDB（fallback）本地数据损坏

- **检测**：每次读取时校验Checksum，不一致即标记损坏
- **恢复**：清除本地ChromaDB，从Supermemory全量重建（按tag拉取所有卡片）
- **预防**：每日自动备份到`~/.memory_backups/`

### 场景C：Obsidian Git仓库损坏/冲突

| 子场景 | 症状 | 处理 |
|--------|------|------|
| Git合并冲突 | push失败，冲突标记残留 | Agent自动检测`<<<<<<<`标记，拉起resolve脚本保留双方内容 |
| .git对象损坏 | git fsck报告错误 | 从最近一个推送到远程的成功commit恢复`git reflog` |
| 远程被强制推送覆盖 | 本地vs远程分歧 | `git pull --rebase` + 自动重写 |
| 误删除整篇笔记 | 文件被rm | Obsidian Git每日备份，从`git log --diff-filter=D`恢复 |

**备份策略**：
```yaml
backup:
  obsidian_vault:
    schedule: "0 3 * * *"       # 每日凌晨3点
    method: git push + tar.gz
    retention: 30天
    remote: origin (GitHub Private)
  supermemory:
    schedule: "0 4 * * *"
    method: API dump all cards → JSON
    retention: 90天
    path: ~/memory_backups/supermemory/
  chromadb_fallback:
    schedule: "0 5 * * *"
    method: cp -r chromadb_dir → backup_dir
    retention: 7天
    path: ~/memory_backups/chromadb/
```

## 七、多Agent协调：冲突检测与消解

### 冲突类型

| 冲突类型 | 示例 | 级别 | 消解策略 |
|---------|------|------|---------|
| **内容覆盖** | A写"渠道ROI=3.2"，B写"渠道ROI=2.9"（同一卡片/笔记） | L2/L3 | 写入前先读+校对，不一致时取平均值+标注分歧 |
| **标签冲突** | A标记#重要，B标记#过期（同一笔记） | L3 | 保留并集，新增`conflict_tag: true`标记 |
| **结构冲突** | A重构了SKILL.md的结构，B按旧格式追加 | L4 | Git merge冲突，由玄骨（shared）Agent主导review |
| **路径冲突** | A和B在同一路径下写同名文件 | L3/L4 | 按`Agent前缀+时间戳`自动重命名（如`渠道分析_梅凝_20260519.md`） |

### 冲突检测机制

```
写入请求 → 检查目标是否存在
    ├── 否 → 直接写入
    └── 是 → 读取现有内容
        ├── 内容相似度≥95% → 跳过（幂等）
        ├── 70%-95% → 差异合并（保留双方，标记分歧）
        └── <70% → 完全冲突 → 暂时阻塞，拉起审批
                         系统通知玄骨Agent → 玄骨判定 → 写入决议
```

### 写锁策略

- **L2卡片**：乐观锁——写入时传入期望的`updated_at`时间戳，服务器端比对后决定是否覆盖
- **L3笔记**：Git分布式——Agent独立写本地branch，push前rebase，冲突走上述检测机制
- **L4技能**：Git PR流程——必须经过玄骨Agent review后合并

## 八、备份策略与恢复流程

### 备份矩阵

| 数据源 | 备份方式 | 频率 | 保留周期 | 恢复RTO | 恢复RPO |
|--------|---------|------|---------|---------|---------|
| L3+L4 Obsidian Git | git push + tar.gz | 每日03:00 | 30天 | <10min | <24h |
| L2 Supermemory | API全量导出→JSON | 每日04:00 | 90天 | <30min | <24h |
| L1（不需要备份） | 自动过期 | — | — | — | — |
| config.yaml | cp到备份目录 | 每次变更 | 永久 | <1min | <1h |

### 恢复流程（含决策树）

```
                              需要恢复
                                  │
                   ┌──────────────┼──────────────┐
                   ▼              ▼              ▼
              Obsidian损坏    Supermemory丢失     config丢失
                   │              │              │
                   ▼              ▼              ▼
             git reflog找回   从JSON备份恢复   从备份目录拷贝
                   │              │              │
         ┌────────┴────────┐     │              │
         ▼                 ▼     │              │
    reflog有效        reflog无效  │              │
         │                 │     │              │
         ▼                 ▼     ▼              ▼
    git reset --hard   从GitHub   API批量导入   重启Agent
    到最后一个commit   clone远程   备份卡片       验证配置
```

### 恢复验证

每月1号自动执行**恢复演习**：
1. 从备份还原一份到`~/memory_backups/test_restore/`
2. 启动测试Agent，随机查询3个知识点
3. 验证命中率≥85%
4. 演习结果写入`/var/log/memory_drill.log`
