# 墨麟OS Obsidian执行规范

---

## 〇、SCQA：为什么需要这个标准

**S（Situation）**：Agent每日产出大量Obsidian笔记，涉及技术决策、操作流程、知识整理、可交付成果四大类内容。

**C（Complication）**：在没有统一标准之前，Agent产出了大量格式混乱的笔记——完整的对话转录文本（"用户说：… 我说：…"），终端命令全文粘贴（含报错堆栈），以及按对话时间戳命名的重复文件（`系统设计-2026-05-19-14-32.md`、`系统设计-2026-05-19-15-07.md`）。这些笔记30天后几乎无法复用，搜索时被240行终端输出淹没，根本找不到结论。

**Q（Question）**：如何确保每篇笔记：30天后仍然有价值？不产生信息垃圾？不会被同类文件淹没？

**A（Answer）**：本规范通过分类判定树消除归类歧义，通过三条质量红线过滤无效内容，通过标准化格式模板确保结构一致，通过禁止模式自动检测防止退化。

## 一、分类判定树

### 判定流程

```
内容来了
  ├─ 这是一个不可逆的选择吗？（技术选型、架构定稿、设计决策）
  │   └─ 是 → 决策/           → 模板：YAML + 背景 → 选项对比 → 决策依据 → 结论 → 后续
  │
  ├─ 这是照着做就能完成的操作步骤吗？（SOP、配置步骤、部署流程）
  │   └─ 是 → 流程/           → 模板：YAML + 前置条件 → 步骤(编号) → 验证方法 → 回滚方案
  │
  ├─ 这是学来的知识吗？（研究结果、架构理解、技术调研）
  │   └─ 是 → 知识/           → 模板：YAML + 核心结论 → 来源 → 推导过程(可选) → 关系链接
  │
  └─ 这是有时间属性的产出物吗？（报告、评审文档、可交付物）
      └─ 是 → 成果/           → 模板：YAML + 摘要 → 正文 → 附件 → 分发对象
```

> **MECE 检查**：四类互斥且完备——任何Obsidian可写入的内容，必落入且只落入其中一类。若不确定，走"决策"类。

### 判定记录（为什么是这四类？）

| 候选方案 | 是否采纳 | 理由 |
|---|---|---|
| 按文件类型（md/pdf/image）分类 | ❌ 否 | 类型是工具属性，不是内容属性，无法指导"如何写" |
| 按项目/领域分类 | ❌ 否 | 项目是标签维度，不是内容维度；一个项目内同样需要决策/流程/知识/成果 |
| 按写作目的分类（说服/记录/参考） | ❌ 否 | 三类互有重叠，难以MECE；同一个技术选型可以同时是"说服"和"参考" |
| 按可复用性分类（一次性/长期/永久） | ❌ 否 | 可复用性是结果不是类别；一篇笔记被归为"一次性"后反而容易写得敷衍 |
| **当前四类（决策/流程/知识/成果）** | ✅ 是 | 互斥、完备、**直接对应模板**——类别决定了"怎么组织内容" |

## 二、三条质量红线

### 红线一：结论还是流水账

**规则**：笔记只保留结论。禁止终端输出全文、对话逐字记录、调试日志原文。

**为什么是这条**：在早期的Agent产出中，约70%的笔记包含完整的对话转录。这些转录占用了95%的字符数，但信息密度接近于零。保留它的唯一理由是"万一以后需要上下文"——但真正的上下文应该被提炼成结论，而不是原文搬运。

**曾考虑但拒绝的方案**：
- _"保留对话转录，但折叠显示"_ → 拒绝。Obsidian折叠后依然占据文件体积，且搜索引擎会索引被折叠的内容，导致检索噪声。
- _"保留最近3轮对话"_ → 拒绝。截断标准太主观，Agent无法可靠判断"哪3轮有意义"。

**执行规则**：
```
任何笔记中不得出现：
- "用户说：…" / "我说：…" 格式的对话轮次
- 整段终端命令输出（>5行为整段）
- 调试日志/堆栈原文（仅保留摘要或关键错误行）
```

**风险场景**：
- 风险：Agent将结论写在末尾，前面仍保留了对话原文。
- 处置：整篇标记为 违规，打回重写。3次违规后 Agent 暂停写入权限24小时。
- 监督：由 nightly review pipeline 自动检测（见第五节）。

---

### 红线二：30天后还值得看吗

**规则**：写之前问自己——这篇笔记30天后还有用吗？没有用就不写。

**为什么是这条**：Obsidian不是聊天记录存档。如果内容在30天内就过期（如"今天装的这个npm包版本号"、临时调试步骤），写进去只会污染搜索。

**曾考虑但拒绝的方案**：
- _"有效期标签 + 自动归档"_ → 拒绝。如果内容30天就没用，为什么要花时间贴标签写归档逻辑？不如不写。
- _"低重要性仍保留，但标记为trash可回溯"_ → 拒绝。可回溯是伪需求——一年后没人会回溯一条"npm装了个什么版本"的笔记。

**执行规则**：
```
写前自问清单：
□ 这篇笔记的核心信息在30天后对我还有其他Agent有用吗？
□ 还是说这只是当前调试/验证中产生的临时信息？

通过 → 写。不通过 → 跳过（可以在terminal日志中留存，不进Obsidian）。
```

**风险场景**：
- 风险：Agent"为了完成任务"强行写低价值笔记。
- 处置：Host通过30天后抽查，低价值率 > 20% 的Agent需重新训练过滤标准。
- 监督：每月一次抽样审查，取当月最后7天写入的笔记。

---

### 红线三：有同主题文件了吗

**规则**：先搜索，再写入。有同主题文件则追加，没有才新建。禁止每次对话新建时间戳文件。

**为什么是这条**：早期数据中，同一主题（如"后端架构选型"）曾被写成5个时间戳文件（`后端架构选型-2026-04-01.md`、`后端架构选型-2026-04-15.md`…）。阅读者需要在5个文件之间跳转比对才知道完整结论。

**曾考虑但拒绝的方案**：
- _"同主题文件用MOC（Map of Content）链接"_ → 拒绝。MOC是事后补救，不是事前预防。更根本的做法是不产生碎片文件。
- _"自动merge时间戳文件"_ → 拒绝。merge时会产生语义冲突，两个时间点的结论可能互相矛盾，Agent没有判断力做自动merge。

**执行规则**：
```
写入前：
1. 用文件名+标签搜索已有文件（至少检查前3个匹配结果）
2. 如果存在同主题文件 → 追加到最新活跃文件的末尾
3. 如果不存在 → 新建

禁止的文件名模式：
- {主题}-{日期}.md          → 如 "后端架构-2026-05-19.md"
- {主题}-{时间戳}.md        → 如 "后端架构-2026-05-19-14-32-08.md"
- {对话摘要}-{日期}.md      → 如 "关于数据库选型的讨论-2026-05-19.md"
```

**风险场景**：
- 风险：Agent故意使用细微不同的主题名来"绕过"搜索匹配（如`后端架构选型.md` vs `后端架构技术选型.md`）。
- 处置：Host月度审查中检查 N-gram 相似度 > 0.7 的文件对，确认是否应合并。
- 监督：自动检测管道每天跑一次重复文件名/相似文件名检查。

```yaml
# 用户量级数据层选型：PostgreSQL + Citus

## 背景

系统需支撑10万用户规模，读写比7:3，单表预计达到500万行/月。需要支持在线schema变更和水平扩展。

## 对比分析

| 维度 | PostgreSQL 16 | TiDB 7.5 | CockroachDB 23.2 |
|---|---|---|---|
| 部署复杂度 | 低（单机 + Citus扩展） | 中（需3个PD+3个TiKV） | 高（需6节点起步） |
| SQL兼容性 | PostgreSQL原生（100%） | MySQL兼容（95%） | PostgreSQL兼容（85%） |
| 水平扩展 | Citus扩展，需改表结构 | 自动分片，无需改表 | 自动分片，无需改表 |
| 10万用户成本 | 单台8C32G ≈ ¥800/月 | 6台4C16G ≈ ¥4800/月 | 6台4C16G + 复本 ≈ ¥6000/月 |
| 运维团队能力 | 团队有3年PG经验 | 需学习TiDB运维 | 需学习CRDB运维 |

## 决策

**选择 PostgreSQL 16 + Citus**。理由：

1. **成本最优**：10万用户规模下TiDB/CRDB的分布式开销完全浪费
2. **团队能力匹配**：现有PG经验可直接复用
3. **演进路径清晰**：若未来超过100万用户，可平滑切换至Citus分布式模式或迁移至TiDB

## 被否决的选项

- **单机PostgreSQL**：单表500万行/月，6个月后查询性能不可接受
- **MongoDB**：业务模型强关联结构，文档数据库不适合现有业务
```

# 一键部署到 staging 环境 - SOP

## 前置条件

- Docker 24+ 已安装
- Docker Hub 账号有 `infra/staging` 仓库写入权限
- 本地 `.env.staging` 文件包含环境变量

### Step 1：构建镜像

```bash
docker build -t infra/staging:$(git rev-parse --short HEAD) .
```

### Step 2：推送镜像

```bash
docker push infra/staging:$(git rev-parse --short HEAD)
```

### Step 3：SSH 到 staging 服务器

```bash
ssh deploy@staging.example.com
```

### Step 4：拉取并重启

```bash
docker pull infra/staging:$(git rev-parse --short HEAD)
docker compose -f docker-compose.staging.yml up -d
```

## 验证方法

```bash
curl -s https://staging.example.com/health | jq .status
```

## 五、禁止内容模式 — 自动检测规则

### 5.1 对话流水账检测

```yaml
# 检测规则（伪代码）
detect_conversation_transcript(content):
  # 规则1：连续出现 "用户说:" / "我说:" / "User:" / "Assistant:" 模式
  if regex_count(r'^(用户[说：:]|我说[：:]|User[：:]|Assistant[：:])', content, multiline=True) > 3:
    return VIOLATION

  # 规则2：对话换行密度异常 - 连续5行以上都是短行（<80字）且有对话特征
  short_lines = count_lines(content, max_length=80)
  total_lines = count_lines(content)
  if total_lines > 20 and (short_lines / total_lines) > 0.6:
    return FLAG_FOR_REVIEW  # 标记人工审查

  # 规则3：包含"今天任务是…" / "我现在开始执行" / "好的我开始" 等开场白
  if regex_match(r'(今天任务|我现在开始|好的我[来开始]|这个任务需要|让我[来先])', content):
    return VIOLATION

  return PASS
```

### 5.2 终端命令全文检测

```yaml
detect_terminal_dump(content):
  # 规则1：存在超过5行的纯 shell 输出块（以 $/⇒/→ 或无前缀的命令行）
  if has_code_block(content, language='bash', min_lines=5):
    return FLAG_FOR_REVIEW

  # 规则2：包含完整堆栈跟踪（Java/Python/Go 异常堆栈特征）
  if regex_match(r'(Traceback \(most recent call last\)|at org\.\w+\.\w+|goroutine \d+)', content):
    return FLAG_FOR_REVIEW

  # 规则3：代码块占比 > 全文50%
  code_ratio = total_code_block_length(content) / total_length(content)
  if code_ratio > 0.5:
    return VIOLATION

  return PASS
```

### 5.3 时间戳文件名检测

```yaml
detect_timestamp_filename(filename):
  # 规则：文件名包含日期模式 2026-05-19 或时间戳模式 2026-05-19-14-32
  if regex_match(r'\d{4}-\d{2}-\d{2}', filename) and not filename.endswith('.md'):
    return PASS  # 不是 markdown 文件，不检测
  if regex_match(r'-\d{4}-\d{2}-\d{2}(-\d{2}(-\d{2}(-\d{2})?)?)?\.md$', filename):
    return VIOLATION

  return PASS
```

### 5.4 重复签名/上下文检测

```yaml
detect_repeated_boilerplate(content):
  # 规则1：同一个 YAML frontmatter 块在文件内重复出现
  frontmatter_count = count_occurrences(content, '---')
  if frontmatter_count > 2:
    return VIOLATION

  # 规则2：Agent 签名/自我介绍连续出现 > 2次
  agent_signatures = ['我是Hermes Agent', '这是由Nous Research开发的', '我是一个AI助手']
  for sig in agent_signatures:
    if count_occurrences(content, sig) > 1:
      return VIOLATION

  # 规则3："我理解你的需求" / "我来帮你" 等冗余开头
  if regex_match(r'^(我理解|我来帮|好的，我来|明白你的|根据你的需求)', content.strip(), multiline=True):
    return FLAG_FOR_REVIEW

  return PASS
```

### 5.5 检查流水线

```
每篇笔记写入后触发（或 nightly batch）：
1. 上述4个检测器并行运行
2. 任何 VIOLATION → 标记违规，通知Host
3. 任何 FLAG_FOR_REVIEW → 加入抽查队列，Host每周review一次
4. 连续3次VIOLATION的Agent → 暂停24小时写入权限
```

## 六、违规文档迁移SOP

当发现已有文档违反本规范时（如旧笔记含对话转录），按以下步骤修复：

### Step 1：评估

```
□ 这篇笔记现在还有价值吗？（30天原则）
  有 → 继续修复
  没有 → 直接归档到 _archive/ 目录，不需要修复
```

### Step 2：提取核心结论

```
1. 通读全文，忽略所有"用户说/我说"的对话轮次
2. 只保留：
   - 最终结论（通常出现在对话后半段）
   - 2-3个支撑理由
   - 下一步行动（如果有）
3. 丢弃：
   - 所有对话轮次
   - 终端命令全文（保留关键行即可）
   - 调试日志原文（保留摘要）
```

### Step 3：重写

```markdown
---
# 用当前规范的三段式重写：结论 → 理由 → 下一步
```

### Step 4：追加或替换

```
如果同主题文件已存在 → 追加到末尾，标记「2026-05-19 修正自旧文档」
如果同主题文件不存在 → 替换原文件
```

### Step 5：验证

```
□ 通过自动检测（4个检测器不报VIOLATION）
□ 无对话流水账
□ 30天后值得看
□ 文件名无时间戳
□ 格式符合模板
```
