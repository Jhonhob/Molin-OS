> **TL;DR — 本文档的核心结论**
>
> Obsidian 中每篇长青文档必须且只需应用六个框架之一：金字塔（结构）、MECE（正交性）、SCQA（背景）、5W1H×SMART（执行）、DIKW（知识边界）、PDCA（迭代）。缺框架的文档应在 48h 内补完标注，否则标记为「未归档」并在每周评审中降级。本规范本身即应用金字塔原理——塔尖 TL;DR 在此，塔身即下方六个框架的独立分节，塔基为每节的表格/模板/示例。

任何写入 Obsidian 的文档，必须围绕一个核心结论展开，绝不交叉遗漏，讲清来龙去脉，让执行可量化，只沉淀知识不堆数据，每次改动留有痕迹。

---

## 决策记录：为什么是这 6 个框架？

| 框架 | 收录原因 | 拒绝的替代方案 |
|------|----------|----------------|
| 金字塔原理 | 唯一解决「文档结构从结论到论据」的模型 | OKR → 聚焦目标而非结构，不适合通用文档 |
| MECE | 唯一保证「分类正交且穷尽」的方法 | 思维导图 → 鼓励发散而非收敛，易遗漏 |
| SCQA | 唯一同时涵盖「背景→冲突→答案」的故事线 | STAR → 偏面试/复盘场景，不适用于前瞻文档 |
| 5W1H×SMART | 唯一将任务描述与量化指标耦合的模板 | GTD → 偏个人任务管理，不适合文档级规范 |
| DIKW | 唯一明确定义「什么该写入 Obsidian」 | KWL → 偏学习场景，缺乏智慧层判断 |
| PDCA | 唯一覆盖「文档演化周期」的迭代模型 | 回顾象限 → 偏团队复盘，不适合单文档演进 |

**核心原则**：六个框架互不重叠——金字塔管结构、MECE 管分类、SCQA 管叙事、5W1H×SMART 管执行、DIKW 管边界、PDCA 管迭代。一篇文档通常只需 1–2 个框架即可覆盖。

## 1. 全局骨架：金字塔原理

**定义**：塔尖 TL;DR（3 句话或 1 个 Blockquote）→ 塔身 H2 分论点（独立、MECE）→ 塔基 H3/表格/代码块。

**示例 — 应用在《2026Q2 搜索延迟优化》文档中**：
```
> TL;DR: 搜索 P95 延迟从 2.3s 降至 0.8s，通过两级缓存 + 读扩散裁剪实现。
## 优化方案
### 预热缓存
### 查询剪枝
## 压测结果
## 回滚方案
```

## 2. 内容拆解：MECE 原则

**定义**：同级条目之间绝无交叉、绝无遗漏。写任何一组并列点前停 3 秒自查。

**示例 — 应用在《系统风险分类》文档中**：

❌ 非 MECE：「基础设施风险」「数据库风险」「硬件风险」—— 数据库属于基础设施，交叉。
✅ MECE：「硬件风险」「软件风险」「网络风险」「人员风险」—— 四者正交且全覆盖。

### MECE 自检清单表

| 待检查项 | 自检问题 | 通过 (✅) | 不通过 (❌) |
|---------|---------|-----------|-----------|
| 正交性 | 任意两个并列条目之间有交叠吗？ | 无交叉 | 有交叉 → 重构 |
| 穷尽性 | 合在一起是否覆盖了所有可能性？ | 全覆盖 | 有遗漏 → 补充 |
| 同一维度 | 所有条目是否按同一标准拆分？ | 是 | 否 → 统一维度 |
| 层次对等 | 每个条目的颗粒度是否一致？ | 是 | 否 → 拉平层级 |
| 无重复 | 同一个概念没有出现在两个条目中？ | 无重复 | 有重复 → 去重 |

## 3. 背景陈述：SCQA 模型

**定义**：S 情境（无争议客观事实）→ C 冲突（打破稳定的问题/痛点）→ Q 疑问（核心课题）→ A 解答（本方案答案）。

**示例 — 应用在《为什么我们切换到 ClickHouse》文档中**：

| 元素 | 内容 |
|------|------|
| **S 情境** | 墨麟 OS 目前日处理分析事件约 2.3 亿条，存储于 PostgreSQL 单实例。 |
| **C 冲突** | 随着业务扩张，Q3 预计日事件量翻倍至 5 亿，PG 单次聚合查询已达 12s，超出 SLO 的 3s 限制。上周已有 3 次生产超时告警。 |
| **Q 疑问** | 如何在控制成本的前提下，将分析查询 P95 延迟降至 1s 以内？ |
| **A 解答** | 迁移至 ClickHouse 集群（3 节点 × 16C/64G），预估年成本增加 $12k，但查询延迟降至 200ms 以内，且支持实时物化视图。 |

## 4. 执行计划：5W1H × SMART

**定义**：六维任务描述，每维绑定 SMART 指标。

### 可粘贴模板

```markdown
## 执行计划

### What（做什么）
描述可交付物：____

### Why（为什么做）
业务价值 / 触发原因：____

### Who（谁负责）
- 执行人：@____
- 审批人：@____
- 知会方：@____

### When（时间节点）
- 开始时间：____-__-__
- 完成时间（DDL）：____-__-__
- 里程碑 1：____-__-__ — ____
- 里程碑 2：____-__-__ — ____

### Where（范围 / 环境）
- 影响模块：____
- 部署环境：____

### How（如何执行）
- 方案简述：____
- 依赖项：____
- 风险预案：____

### SMART 量化检查
- [ ] S — 具体：交付物是否有明确描述？
- [ ] M — 可衡量：完成状态如何验证？（PASS/FAIL 标准）
- [ ] A — 可达到：在当前资源和时间下可行？
- [ ] R — 相关：与文档核心结论一致？
- [ ] T — 有时限：DDL 是否明确？
```

## 5. 知识边界：DIKW 金字塔

**定义**：D 原始数据 → I 整理信息 → K 已验证模型/SOP → W 核心价值观/战略方向。Obsidian 应只存 K 和 W，D 和 I 由 Hermes Agent 或外部系统托管。

### 内容适用性决策流程图

```
某条信息 → 它是原始数据（CSV/JSON/日志）吗？
    ├── 是 → ❌ 不入 Obsidian，放在 `数据层/` 或外部数仓
    └── 否 → 它是经过整理的图表/报告吗？
         ├── 是 → ❌ 不入 Obsidian（除非作为知识附注参考），放在 `信息层/`
         └── 否 → 它是可复用的模型/SOP/方法论吗？
              ├── 是 → ✅ 入 Obsidian（Knowledge），放在 `系统层/`
              └── 否 → 它是战略方向/价值观/决策原则吗？
                   ├── 是 → ✅ 入 Obsidian（Wisdom），放在 `战略层/`
                   └── 否 → ❌ 暂不入库，先归类再判断
```

## 6. 迭代机制：PDCA 循环

**定义**：文档末尾 Changelog 必须包含做了什么修改及为什么改。每次变更 = 一个 PDCA 小循环。

## 文档交叉引用格式

所有提及其他文档处，必须使用 `[[文档名#标题]]` 格式，而非纯文字引用。示例：

- ✅ `详见 [[数据层/数据字典#用户表结构]]`
- ✅ `降级策略参见 [[系统层/架构演进/容灾方案#降级预案]]`
- ❌ ~~详见“数据字典”文档~~
- ❌ ~~参见第 3 节降级预案~~

### 不合规处置

| 场景 | 风险 | 自动检测手段 |
|------|------|-------------|
| 文档无任何框架标注 | 结构不可靠，误读风险高 | Hermes Agent 每周扫描 frontmatter `frameworks_applied` 字段，生成本周缺失清单 |
| 文档标注框架但未按框架写作 | 标注虚假，降低其他文档可信度 | 人工评审 + Hermes 抽查：随机抽 30% 已标注文档验证一致性 |
| 文档内容跨越 3+ 框架却只标 1 个 | 框架覆盖不全 | Hermes 自动检测正文中的框架模式，建议补标 |

**行动规则**：未标注框架的文档将在每周四的「内容评审」中被标记为「未归档」，连续 2 周未归档的文档移至 `归档/`。
