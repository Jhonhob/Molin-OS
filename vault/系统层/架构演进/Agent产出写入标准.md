> **TL;DR — 核心结论**
>
> 所有Agent产出统一使用 `业务线|内容.md` 命名规范写入四层目录体系，禁止写入任何废弃路径。本标准的每一条规则都有反面案例支撑——命名混乱导致文件不可查、目录错放导致记忆检索断裂、废弃路径写入导致Agent同步死锁。遵守本标准是Agent产出可检索、可复用、可审计的前提。

## SCQA：为什么需要这份写入标准？

### S 情境

墨麟OS已接入5个Agent（玄骨中枢、元瑶教育、银月传媒、梅凝出海、宋玉创业），每天自动产生数十份文档——内容包括架构决策、产品定义、市场分析、财务报告、行业研究。这些文档通过记忆同步流水线（每小时触发）自动写入Obsidian vault的`系统层/`、`业务层/`、`运营层/`、`知识库/`四层目录。

同步流水线包含4个脚本接力执行：
```
sync_memory.py    → 会话记忆分类写入
obsidian_sync.py  → 报告同步
collect_architecture.py → 架构采集
relay_to_obsidian.py    → Relay产出写入
```
（参见 [[系统层/部署与环境/Obsidian工作流标准]]）

### C 冲突

标准化之前，多个Agent并行产出时发生了以下问题：

| # | 问题 | 后果 | 发生次数 |
|---|------|------|---------|
| 1 | 同一份文档被不同Agent写入不同路径 | 记忆检索出现两份"几乎一样"的结果，RAG召回分裂 | 6+次 |
| 2 | 文件名乱用分隔符：`元瑶教育_20260519_Q2计划.md`、`元瑶教育-20260519-Q2计划.md`、`元瑶教育20260519Q2计划.md` | 按`|`检索时完全漏掉；按文件名排序时FIFO序列混乱 | 12+次 |
| 3 | 内容写入废弃路径（`agent-outputs/`、`02_Agent_Outputs/`），这些目录不在Obsidian索引范围 | 文档存在但永远检索不到，Agent自认为已写入 | 4次 |
| 4 | 飞轮管线第三棒依赖第二棒写入的路径查找上游产物——路径写错则飞轮断裂 | 内容生产链中断，告警不能自动修复 | 3次 |

### Q 疑问

如何在Agent生态持续扩张（5→22家Worker）的情况下，确保每一次产出都被写入正确的位置、拥有可预测的命名、不会因路径混乱导致检索断裂？

### A 解答

四层目录体系 + `业务线|内容.md` 命名规范 + 防复发自动扫描。具体见下文。

## 一、命名规范设计决策记录

### 1.1 为什么是 `业务线|内容.md`？

| 候选方案 | 示例 | 被拒绝的原因 |
|---------|------|-------------|
| ✅ **`业务线|内容.md`** | `元瑶教育|Q2课程计划.md` | 选定方案 |
| ❌ `YYYY-MM-DD_内容.md` | `2026-05-19_Q2课程计划.md` | 时间前缀炸散同一业务线的文档序列，检索时无法按业务线聚合 |
| ❌ `Agent名-内容.md` | `edu-Q2课程计划.md` | Agent名与业务线映射不稳定（Agent可被重新分配）；跨Agent协作产生的文档归属不清 |
| ❌ `内容_业务线.md` | `Q2课程计划_元瑶教育.md` | 打字友好度差，文件名中汉字后缀导致Tab补全困难 |
| ❌ `内容.md`（无前缀） | `Q2课程计划.md` | 多Agent写入时极易命名冲突——银月传媒和梅凝出海都可能产生"市场分析" |

**核心原则**：垂直分割（按业务线）+ 水平分割（按内容语义），`|`作为唯一合法分隔符。业务线在前确保文件按业务线自然聚合在同一目录下排序连续。

### 1.2 为什么是四层目录而非平铺？

`业务层/`、`运营层/`、`系统层/`、`知识库/` 四层的MECE正交性验证：

| 层        | 内容类型               | DIKW映射                | 检索优先级  | 排除的替代方案                    |
| -------- | ------------------ | --------------------- | ------ | -------------------------- |
| **系统层/** | 技术底座、架构演进、环境规范     | K（Knowledge）          | ★★★ 最高 | ❌ `技术/` — 与业务/运营交叉模糊       |
| **业务层/** | 产生直接价值的项目、产品线、商业方案 | K+W（Knowledge+Wisdom） | ★★★    | ❌ `产品/` — 无法容纳服务型业务（教育、咨询） |
| **运营层/** | 日常运转、市场增长与商业化洞察    | K（Knowledge）          | ★★     | ❌ `市场/` — 无法涵盖财务、法务、内部运营   |
| **知识库/** | 深度加工后的行业研报与技术长文    | K（Knowledge）（外部）      | ★★     | ❌ `研究/` — 与业务层的"调研"字段重叠    |

**为什么不是更多层？** 5+层会增加Agent分类决策的出错率——实测Agent判断"一篇内容该放A还是B"时的误判率在3层以下<5%，5层以上升至15%+。4层是精准度与覆盖度的平衡点。

## 四、完整写入流程场景

### 场景：银月传媒Agent执行"小红书内容创作"任务

```
Step 1 ─ Agent收到指令
        指令: "为墨麟OS写一篇小红书宣传文案"
        执行Agent: media（银月传媒）

Step 2 ─ 分类决策
        问题: 这篇产出的DIKW层级是什么？
              → K（可复用的SOP/方法论/输出物）
        问题: 属于哪个业务线？
              → 银月传媒 → 业务层/自动化工作流/
        问题: 文件名用什么？
              → `银月传媒|小红书宣传文案.md`

Step 3 ─ 构造完整写入路径
        路径: 业务层/自动化工作流/银月传媒|小红书宣传文案.md
        验证: path not in 废弃路径列表 ✓
              parent_dir 存在 ✓

Step 4 ─ 写入前检查
        - 同名文件检查: 该路径下无冲突 ✓
        - YAML frontmatter 检查: 是否包含 title/status/agent_sync ✓
        - TL;DR 检查: 是否有 Blockquote 开头 ✓

Step 5 ─ 写入文件
        ┌─────────────────────────────────────────┐
        │ ---                                    │
        │ title: 小红书宣传文案                   │
        │ status: 活跃                           │
        │ last_updated: 2026-05-19               │
        │ agent_sync: true                       │
        │ agent: media                           │
        │ business_line: 银月传媒                 │
        │ collaborators: []                      │
        │ ---                                    │
        │                                        │
        │ > TL;DR — 为墨麟OS设计的小红书文案...   │
        │                                        │
        │ ## 正文                                │
        │ ...                                    │
        └─────────────────────────────────────────┘

Step 6 ─ 确认写入
        写入路径记录到Agent会话记忆
        记忆同步流水线下一轮自动同步到Supermemory
```

## 五、重命名与迁移SOP

### 5.1 检测触发条件

当以下任一条件触发时执行重命名/迁移：

1. **健康检查发现**：文件位于废弃路径或错误目录（见 §7.2 失败处理）
2. **业务线重命名**：子公司改名或业务线重组
3. **手动发现**：人工审查发现文件归类错误

### 5.2 标准迁移流程

```
Step 1 ─ 识别异常
        扫描找到: 02_Agent_Outputs/edu/plan.md
        目标路径: 业务层/项目全生命周期/元瑶教育|计划.md

Step 2 ─ 修复内容
        1. 读取原文件
        2. 更新 YAML frontmatter（修正 title、agent、business_line）
        3. 更新内部 [[wikilink]] 引用（如果原路径被其他文档引用）
           → 使用 git grep 或 ripgrep 搜索 vault 内所有引用路径
        4. 将文件名改为符合规范的 `业务线|内容.md` 格式

Step 3 ─ 移动文件
        mv "02_Agent_Outputs/edu/plan.md" "业务层/项目全生命周期/元瑶教育|计划.md"

Step 4 ─ 更新引用
        遍历所有引用旧路径的 [[wikilink]]，替换为新路径
        示例: [[02_Agent_Outputs/edu/plan]] → [[业务层/项目全生命周期/元瑶教育|计划]]

Step 5 ─ 验证
        1. 确认新路径文件可正常打开
        2. 确认所有引用链接跳转到新路径
        3. 在废弃路径检查中确认原路径不再出现

Step 6 ─ 记录
        在 Changelog 追加迁移记录：
        | 2026-05-19 | 迁移 | edu/plan.md → 业务层/项目全生命周期/元瑶教育|计划.md | 健康检查发现 |
```

### 5.3 批量迁移

超过5个文件的批量迁移使用脚本自动执行：

```bash
# 伪代码——实际执行用 molib CLI
python -m molib vault migrate \
  --from "02_Agent_Outputs/**/*.md" \
  --to-map '{"edu": "业务层/项目全生命周期/", "media": "业务层/自动化工作流/"}' \
  --dry-run  # 先预览，确认后去掉 --dry-run
```

## 六、冲突解决

### 6.1 同一目录同时写入冲突

两个Agent（或同一Agent的两次执行）在同一秒写入同一路径：

| 场景 | 影响 | 解决方案 |
|------|------|---------|
| 完全相同路径+内容 | 无影响（幂等写入） | 直接覆盖，不告警 |
| 完全相同路径+不同内容 | 后写入者覆盖前者，前一份内容丢失 | 该路径加时间戳后缀 `|冲突-20260519-181500.md`，原始路径保留最后一次写入；Agent日志记录冲突事件 |

**实现机制**：`output_writer.py` 在执行 `write_file` 前：
1. 检查目标路径是否存在
2. 如果存在且内容不同 → 追加时间戳后缀，记录双写日志
3. 如果存在且内容相同 → 跳过写入（幂等）

### 6.2 文件名冲突（不同Agent同路径不同内容）

示例：`业务层/项目全生命周期/市场分析.md` 同时被元瑶教育和梅凝出海使用。

| 解决方式 | 适用条件 | 操作 |
|---------|---------|------|
| 自动重命名 | 两份内容无必然联系 | 后写入者改为 `业务线|市场分析.md` |
| 合并 | 两份内容互补 | 人工判断是否合并为单一文档 |
| 分拆子目录 | 两者长期都需要"市场分析" | 创建 `元瑶教育/` 和 `梅凝出海/` 子目录 |

**优先策略**：先自动重命名，次日健康检查时人工确认是否需要合并或分拆。

### 6.3 废弃路径冲突

如果发现两个Agent同时往废弃路径写入，立即：
1. 锁定该废弃路径（chmod 000）
2. 反转两个Agent的写入配置
3. 记录事故到Agent日志
4. 触发T4飞书告警

## 八、风险登记与兜底

### 8.1 风险矩阵

| 风险 | 概率 | 影响 | 等级 | 检测手段 | 兜底方案 |
|------|------|------|------|---------|---------|
| 健康检查脚本静默失败 | 中 | 高：违例堆积，数周后才发现 | **P0** | 双保险：Hermes cron自带执行状态码 + 每次同步后向飞书发确认消息 | 如果连续2次未收到检查确认 → 触发T4告警"Vault合规检查可能失联"；人工执行 `python -m molib ghost-os health` 手动触发 |
| 人工手动写入废弃路径 | 低 | 中：单次文件不可达 | **P1** | 废弃路径目录权限设为只读（chmod 555） | 周检自动发现并迁移；紧急时可临时打开权限 |
| 多Agent并发写入相同路径 | 低 | 中：内容丢失 | **P1** | output_writer.py 内置冲突检测（见 §6.1） | 时间戳后缀保留两份内容，冲突日志可追溯 |
| 业务线映射表过期 | 中 | 高：新业务线写入错误目录 | **P0** | 每次新增Agent/Worker时强制更新映射表；Agents.md 与映射表保持同步 | 新Agent无法通过写入前路径验证 → 写入失败并告警，等待人工映射 |
| 路径中非法字符 | 低 | 低：文件名含 `: / \` 导致系统写入失败 | **P2** | output_writer 在写入前对文件名做 sanitize（替换非法字符为 `_`） | 写入失败时记录原始名和sanitized名到日志 |
| 四层目录不存在 | 低 | 中：写入失败 | **P1** | output_writer 在写入前 `mkdir -p` 自动创建 | 如果创建失败（权限问题）→ 降级写入临时目录并告警 |

### 8.2 健康检查失败时的级联保护

```
Vault合规周检触发
  ├── 成功 → 检查结果写入 relay/ → 无告警
  └── 失败（脚本异常/超时/LLM不可用）
       ├── 重试策略: 15分钟后重试1次
       ├── 仍失败 → 跳过本次检查，记录失败事件
       ├── 连续2次失败 → 触发T4飞书告警
       └── 连续4次失败 → 降级为简易检查（仅做废弃路径grep，不做语义分析）
```
