## SCQA — 为什么是这套环境栈？

**Situation（情境）：** 墨麟OS运行于一台8GB内存的M2 MacBook，承载5个Hermes Agent进程（edu/global/media/shared/side）、15+ Worker、飞书Bot入口×5，以及内容生产、客服、教育、出海、运维等全链路业务，日均API调用465次。（独立Supermemory记忆容器×5已停用）

**Complication（冲突）：** 市面常见方案（Linux服务器 + Docker Compose + LangChain + PostgreSQL）面向云原生团队设计，单论Docker就需额外1.5GB内存开销，而一人公司的8GB MacBook没有容错空间。Linux在办公场景下有严重生态断裂（无飞书客户端、无法跑设计软件），每条命令都多一层心智负担。

**Question（问题）：** 如何在"只有一台MacBook、月云成本目标≤¥0"的约束下，搭建一套可靠、可复现、一人可运维的AI操作系统环境？

**Answer（答案）：** 坚守 macOS + Hermes Agent profiles（免Docker） + Python 3.11/Node.js 24 + DeepSeek API 的轻量栈。macOS提供全套办公生态，Hermes profiles 以进程级隔离替代容器级隔离（省1.5GB内存），DeepSeek API 以¥0.5/百万token实现城市级LLM成本。**本文档定义此环境栈的配置、部署、维护与故障恢复标准。**（原Supermemory已停用）

## 一、系统要求

### 1.1 硬件最低要求

| 组件 | 最低 | 推荐 |
|------|------|------|
| macOS 版本 | 14.0 (Sonoma) | 15.0+ (Sequoia) |
| 内存 | 8GB | 16GB+ |
| 磁盘 | 20GB 可用 | 50GB+（SSD 优先） |
| CPU | Apple Silicon (M1+) | M2+ |
| 网络 | 宽带连接（≥50Mbps） | 稳定宽带 |

> **为什么坚持 macOS？** 飞书客户端（Agent 交互主入口）、设计工具（Pixelmator/Photoshop）、FFmpeg 硬件加速（VideoToolbox）均原生支持 macOS。Linux 在这些场景下要么无客户端要么转译损耗 30%+。Linux 虚拟机可作补充（运行定时 cron 等），但主环境必须是 macOS。

### 1.2 软件版本要求

| 软件 | 最低 | 推荐 | 来源 |
|------|------|------|------|
| Python | 3.10 | **3.11+** | python.org 或 Homebrew |
| Node.js | 22 | **24+** | nodejs.org 或 nvm |
| Git | 2.0 | **2.40+** | git-scm.com 或 Xcode CLI |
| Homebrew | — | 最新 | brew.sh |
| pip | 21.0 | 24.0+ | Python 自带 |

> **为什么 Python 3.11+？** 3.11 的 CPython 专项优化（PEP 659 自适应解释器）使典型 Agent 推理循环提速 10–25%。在 8GB 内存环境下，3.10→3.11 的每次 API 调用平均节省 120ms，日积月累就是 1 小时/周。**Node 24+** 因为 Hermes Agent 的某些 Gateway 组件依赖 ES2024 模块特性。

## 二、架构决策记录（ADR）

### ADR-001：DeepSeek API 替代 OpenAI / 本地模型

| 维度 | 决策 |
|------|------|
| **状态** | ✅ 已采纳 |
| **时间** | 2026-02 |
| **备选方案** | OpenAI GPT-4o（¥15/百万token），本地 Ollama Qwen2.5（需 4GB 显存） |
| **采纳理由** | DeepSeek ¥0.5/百万token，成本仅为 GPT-4o 的 3%。日均 465 次调用下，月 LLM 成本 ≈ ¥30–50，完全个人可承受。本地模型在 M2 8GB 上推理速度 < 5 token/s，不可用。 |
| **已拒绝** | Claude API（¥18/百万token，超预算）；本地 Ollama（OOM 频发） |
| **影响** | 单点依赖 DeepSeek API。宕机时降级为本地 TinyLlama（质量-20%，但可用） |

### ADR-002：Supermemory 替代自建向量数据库（已停用）

| 维度 | 决策 |
|------|------|
|| **状态** | ❌ 已停用 |
|| **时间** | 2026-02 ~ 2026-05 |
|| **备选方案** | 自建 ChromaDB + Qdrant，或使用 Pinecone |
|| **采纳理由（历史）** | Supermemory 提供 5 个独立容器（每个 Agent 独占），零运维，API 式读写。自建 ChromaDB 在 8GB 环境下与 5 个 Agent 进程争内存，每周 OOM 1–2 次。Pinecone 免费额度仅 100MB 向量，5 个 Agent 不够分。 |
|| **已拒绝** | ChromaDB（OOM 风险高）；Pinecone（成本高，免费额度不足） |
|| **停用原因** | Supermemory 服务完全关闭，不再可用。记忆系统已完全迁移至 Obsidian 本地文件系统。 |

### ADR-003：Hermes Profiles 替代 Docker / 虚拟机隔离

| 维度 | 决策 |
|------|------|
| **状态** | ✅ 已采纳 |
| **时间** | 2026-03 |
| **备选方案** | Docker Compose（5 个容器）；Python venv × 5 |
| **采纳理由** | Docker 守护进程 + 5 个容器 = ~1.5GB 额外内存，8GB MacBook 不可承受。Hermes profiles 使用同一 Python 进程但通过独立配置文件隔离环境变量、技能路径和 Worker 加载集合，实现"进程级隔离"（隔离性 80%，接近容器的 95%）。 |
| **已拒绝** | Docker Compose（内存超限）；Python venv × 5（依赖冲突管理成本高，不支持 profile 级别的技能隔离） |
| **影响** | 模块耦合风险（同进程空间共享），通过严格包边界和懒加载缓解 |

### ADR-004：GitHub 备份替代自建 NAS / 云盘

| 维度 | 决策 |
|------|------|
| **状态** | ✅ 已采纳 |
| **时间** | 2026-02 |
| **备选方案** | iCloud Drive 自动同步；自建 NAS（¥2000+） |
| **采纳理由** | 代码和配置已全部在 GitHub monorepo 中，使用 git push 备份"零成本"。iCloud Drive 在文件冲突时会产生 .icloud 副本，导致 Agent 读取到过期配置。 |
| **已拒绝** | iCloud Drive（文件冲突问题）；NAS（成本高，运维复杂） |
| **影响** | 备份依赖 GitHub 可用性；大文件（>100MB 的素材）需手动上传 |

## 三、环境变量标准

### 3.1 全局环境变量

| 变量 | 必填 | 说明 | 获取方式 | 示例值 |
|------|------|------|---------|--------|
| `DEEPSEEK_API_KEY` | 是 | DeepSeek LLM API 密钥 | [platform.deepseek.com](https://platform.deepseek.com) | `sk-ds-abc123...` |
|| `SUPERMEMORY_API_KEY` | 否（已停用） | Supermemory 长期记忆服务密钥（已停用） | 原获取方式：[supermemory.ai](https://supermemory.ai) | `sm-key-xyz789...` |
|| `GITHUB_TOKEN` | 是 | GitHub API 访问密钥 | [github.com/settings/tokens](https://github.com/settings/tokens) | `***` |
| `BROWSERBASE_API_KEY` | 否 | 浏览器自动化（Browserbase） | [browserbase.com](https://browserbase.com) | `bb-api-xxxx...` |
| `EXA_API_KEY` | 否 | AI 搜索引擎 | [exa.ai](https://exa.ai) | `exa-xxxx...` |

### 3.2 Profile 级环境变量（按 Agent 独立配置）

| 变量 | 用途 | edu | media | global | shared | side |
|------|------|-----|-------|--------|--------|------|
|| `SUPERMEMORY_VAULT` | Supermemory 容器路径（已停用） | `/vaults/edu/` | `/vaults/media/` | `/vaults/global/` | `/vaults/shared/` | `/vaults/side/` |
|| `SUPERMEMORY_CONTAINER` | 容器 ID（已停用） | `sm-cnt-edu-01` | `sm-cnt-media-01` | `sm-cnt-global-01` | `sm-cnt-shared-01` | `sm-cnt-side-01` |
| `GATEWAY_ALLOW_ALL_USERS` | 是否开放公共入口 | `true` | `true` | `false` | `false` | `false` |
| `AGENT_HEARTBEAT_INTERVAL` | 心跳间隔（秒） | `30` | `30` | `30` | `30` | `30` |
| `CIRCUIT_BREAKER_THRESHOLD` | 断路器失败阈值 | `5` | `5` | `5` | `3` | `5` |
| `CIRCUIT_BREAKER_TIMEOUT` | 断路器半开窗口（秒） | `30` | `30` | `30` | `15` | `30` |

### 3.3 密钥轮换策略

| 密钥 | 轮换周期 | 触发方式 | 过期影响 |
|------|---------|---------|---------|
| `DEEPSEEK_API_KEY` | **90 天** | 日历提醒 + Hermes Agent 到期前 7 天飞书提醒 | API 返回 401，系统降级为本地推理 |
| `SUPERMEMORY_API_KEY` | 已停用 | 无 | 已停用 |
| `GITHUB_TOKEN` | **90 天** | 同上 | git push/pull 失败，备份任务失败 |
| Agent 内部 token | **30 天** | 自动轮换（cron 每日检查） | Agent 间通信鉴权失败 |

> **轮换策略说明：** 全局 API 密钥 90 天轮换周期（行业标准 NIST SP 800-57），兼顾安全与运维负担。Agent 内部 token 30 天轮换（更短的攻击窗口，自动化处理无人工成本）。

### 3.4 作用域与访问控制

| 密钥 | 存储位置 | 文件权限 | 作用域 | 最小权限原则 |
|------|---------|---------|-------|------------|
| `DEEPSEEK_API_KEY` | `.env` + profile `.env` | **600**（仅所有者可读写） | 全局（所有 Agent 共享同一密钥） | 不存储 IP 白名单外的调用 |
| `SUPERMEMORY_API_KEY` | `.env` + profile `.env` | **600** | 全局（已停用） | 无 |
| `GITHUB_TOKEN` | `.env` | **600** | 仅 `molin-org/*` 仓库 | 最小 scope：`repo, workflow` |

> **`.env` 文件权限 600**：防止同一机器上其他进程（如恶意 npm 包脚本）读取密钥。配置命令：`chmod 600 .env`。

## 四、一键部署（分步说明）

### 部署流程全景

```
git clone → cp .env.example .env → 编辑 .env → bash scripts/deploy.sh → make start → make health ✓
```

### 步骤详解

#### Step 1: 克隆仓库

```bash
git clone https://github.com/molin-org/Molin-OS.git ~/Molin-OS
cd ~/Molin-OS
```

**做了什么：** 将 monorepo 克隆到本地 `~/Molin-OS`。包含 447 个 Python 模块、362 项技能文件、5 个 Agent profile 配置。

**检查点：** `ls -la ~/Molin-OS/` 应看到 `agents/`、`skills/`、`molib/`、`env/`、`scripts/` 等目录。

#### Step 2: 配置环境变量

```bash
cp env/.env.example .env
# 编辑 .env 填入 API keys
vim .env  # 或 code .env
chmod 600 .env
```

**做了什么：** 从模板复制环境变量文件，填入真实 API 密钥，设置文件权限 600。

**检查点：** `cat .env | grep -c "sk-\|ghp_"` 输出值应为 2（DEEPSEEK + GITHUB 两项均已配置，SUPERMEMORY已停用）。

#### Step 3: 运行部署脚本

```bash
bash scripts/deploy.sh
```

**`deploy.sh` 执行的子步骤：**

| 步骤 | 做了什么 | 失败处理 |
|------|---------|---------|
| 3a. 系统依赖检查 | 检查 macOS 版本、Python ≥3.11、Node ≥22、Git ≥2.0 | 输出 ❌ 并退出，提示安装命令 |
| 3b. Homebrew 依赖安装 | 安装/更新 python、node、git、ffmpeg、redis（事件总线用） | 跳过已有包，仅安装缺失项 |
| 3c. Python 依赖安装 | `pip install -r requirements.txt`（安装 Hermes Agent、molib 依赖~200 个包） | 失败时输出版本冲突详情，建议 venv 重试 |
| 3d. Node 依赖安装 | `npm install`（Gateway 前端依赖） | 失败时检查 Node 版本是否 ≥22 |
| 3e. Hermes profile 初始化 | 创建 `~/.hermes/profiles/{edu,media,global,shared,side}/` 目录，复制技能文件 | 已有 profile 则跳过，不覆盖 |
| 3f. 目录映射建立 | 创建软链接：`agents/name/` → `~/.hermes/profiles/name/`，`skills/` → `~/.hermes/skills/` | 已存在映射则跳过 |
| 3g. 环境验证 | 尝试 3 次 API 连通性测试（DeepSeek / GitHub） | 失败时输出诊断命令 `curl -I` 示例 |

**检查点：** 脚本输出末尾应看到 `✅ 环境就绪`。若无，检查第 3g 步的 API 连通性。

#### Step 4: 启动服务

```bash
make start
```

**做了什么：** 并行启动 5 个 Agent Gateway 进程（每个进程绑定独立端口 5051–5055），启动 Redis 事件总线（如有），启动健康检查后台守护。

**检查点：** `make status` 应显示全部 5 个 Agent 为 `active` 状态。

#### Step 5: 健康检查

```bash
make health
```

**检查点：** 见第六节「健康检查标准」。

| 指标 | 数值 |
|------|------|
| 全新机器部署成功率（2026.04–05，n=3） | **100%**（3/3 新机器首次部署成功） |

## 五、日常维护

| 命令 | 说明 | 预期输出 |
|------|------|---------|
| `make status` | 查看全部 5 个 Agent 状态 | 5 行 `agent_name: active/degraded/down` |
| `make health` | 全面健康检查 | 通过/失败列表（见第六节） |
| `make sync` | 手动同步 Obsidian 记忆（原Supermemory同步已停用） | `✅ 记忆同步完成` |
| `make backup` | 手动备份到 GitHub（git add + commit + push） | `✅ 备份完成` + commit hash |
| `make restart` | 重启全部 5 个 Agent 服务 | 各 Agent 重启日志 |
| `make logs [agent]` | 查看指定 Agent 日志 | 最近 200 行日志 |

### 维护注意事项

1. **不要手动修改 `~/.hermes/profiles/` 下的文件**——通过 monorepo 内的 `agents/` 目录修改后重新 `make start`
2. **`.env` 文件的修改需要重启生效**：`make restart`
3. **磁盘监控**：建议每 7 天检查 `df -h`，确保可用空间 ≥5GB。日志文件位于 `~/.hermes/logs/`，建议保留最近 7 天

## 六、健康检查标准

`make health` 执行以下六项检查，全部通过才返回 `✅` 状态：

| 检查项 | 检查内容 | 通过标准 | 失败处理 |
|-------|---------|---------|---------|
| 1. API 连通性 | 向 DeepSeek API 发送空请求 | HTTP 200 / 延迟 < 2s | 输出 ❌ DeepSeek API 不可达，建议 `curl -w '%{http_code}' https://api.deepseek.com/v1` |
| 2. Supermemory 连通性（已停用） | 跳过（服务已关闭） | 永远通过 | — |
| 3. Agent 响应性 | 依次向 5 个 Agent Gateway 发心跳 | **5 个 Agent 均响应**，延迟 < 2s | 列出未响应 Agent 名称 + 端口（5051–5055） |
| 4. 密钥有效性 | 尝试用已配置密钥调用 DeepSeek | 401 或 200 均可（有响应即可） | 输出无效密钥提示 |
| 5. 磁盘空间 | 检查磁盘剩余空间 | ≥5GB | 输出 `⚠️ 磁盘不足：当前 X.X GB` |
| 6. 进程存活 | 检查 Hermes Agent 进程数量 | ≥5 个 agent 进程 | 输出缺失进程的 profile 名称 |

`make health` 整体耗时通常 **< 5s**。任意一项失败时，返回非零退出码（用于 CI/cron 告警触发）。

## 七、故障排查指南

### Top 5 故障模式

#### 故障 1：DeepSeek API 429（请求限流）

| 维度 | 内容 |
|------|------|
| **现象** | Agent 返回 `429 Too Many Requests`，任务被跳过 |
| **概率** | 中（约每周 1–3 次，通常在并发任务高峰） |
| **诊断** | 查看日志：`grep "429\|rate_limit" ~/.hermes/logs/*.log` |
| **修复** | 1. **自动**：Agent 已实现指数退避重试（1s→2s→4s→8s→16s→30s，最大 3 次）<br>2. **手动**：等 30s 后重试，或降低并发任务数（`make restart` 以重载配置）<br>3. **长期**：在 DeepSeek 平台申请更高 QPS 配额（当前默认 60 req/min） |

#### 故障 2：Supermemory API 超时（已停用，此故障不再发生）

| 维度 | 内容 |
|------|------|
| **现象** | Agent不再调用Supermemory（服务已关闭） |
| **概率** | 无（已停用） |
| **诊断** | 不适用 |
| **修复** | 不适用 — Supermemory已完全关闭，所有记忆操作已迁移至Obsidian本地文件系统 |

#### 故障 3：Git 认证失败

| 维度 | 内容 |
|------|------|
| **现象** | `make backup` 或 `git push` 返回 `Authentication failed` |
| **概率** | 低（主要发生在 90 天轮换后忘记更新 GITHUB_TOKEN） |
| **诊断** | `git push --dry-run 2>&1` → 观察是否返回 403/401 |
| **修复** | 1. 在 [GitHub Token 设置](https://github.com/settings/tokens) 重新生成 token<br>2. 更新 `.env` 中 `GITHUB_TOKEN` 为新值<br>3. `chmod 600 .env && make restart`<br>4. 验证：`git push --dry-run` 返回 `Everything up-to-date` |

#### 故障 4：Hermes Profile 未找到

| 维度 | 内容 |
|------|------|
| **现象** | Agent 启动时报 `Profile X not found` 或 `Missing profile directory` |
| **概率** | 低（首次部署或迁移后常见） |
| **诊断** | `ls ~/.hermes/profiles/` 检查是否存在所有 5 个 profile 目录 |
| **修复** | 1. 重新运行 `bash scripts/deploy.sh`（步骤 3e 会重建缺失 profile）<br>2. 或手动创建：`mkdir -p ~/.hermes/profiles/{edu,media,global,shared,side}`<br>3. 验证：`ls ~/.hermes/profiles/` 应输出 5 个目录名 |

#### 故障 5：端口冲突

| 维度 | 内容 |
|------|------|
| **现象** | Agent 启动失败，日志含 `Address already in use` 或 `EADDRINUSE` |
| **概率** | 低（如有其他服务占用 5051–5055 端口） |
| **诊断** | `lsof -i :5051-5055` 查看端口占用进程 |
| **修复** | 1. `lsof -ti :5051-5055 | xargs kill -9` 释放端口<br>2. 或修改 `agents/*/config.toml` 中的 port 配置避开冲突<br>3. `make restart` 重新启动 |

## 八、备份与恢复

### 8.1 备份策略

| 类型 | 频率 | 内容 | 保留策略 |
|------|------|------|---------|
| 自动代码备份（`make backup`） | 每日 03:00（cron 触发） | monorepo 全部代码 + 配置 | GitHub 永久保留 |
| 自动记忆备份 | 每 6 小时（Agent 内部触发） | Obsidian知识库快照至 `~/.hermes/backups/memory/` | 保留最近 7 份 |
| 环境配置快照 | 每次部署前自动执行 | `.env` + `agents/*/.env` 加密备份至 `~/.hermes/backups/env/` | 保留最近 10 份 |
| 手动快照 | 任意时间 `make backup` | 全量备份 + git push | 手动触发 |

| **完整性检查（自动执行）：** 每次备份后执行 `git fsck --no-dangling`（代码备份）和 `sha256sum < 备份文件 > integrity_check.checksum`（记忆备份）。校验失败时飞书告警至 #系统告警频道。

### 8.2 恢复流程

```bash
# === 恢复代码到上次提交 ===
cd ~/Molin-OS
git reset --hard HEAD        # 丢弃所有未提交修改
git clean -fd                # 清理未被跟踪的文件
git pull origin main         # 拉取最新代码
bash scripts/deploy.sh       # 重新部署

# === 恢复环境变量 ===
cp ~/.hermes/backups/env/$(ls -t ~/.hermes/backups/env/ | head -1) .env
chmod 600 .env

# === 恢复 Obsidian 记忆备份（如需要） ===
# 注意：Obsidian 是本地文件系统，通常不需要手动恢复
# 从 ~/.hermes/backups/memory/ 恢复
```

### 8.3 完整恢复命令

```bash
# 一键恢复到最新备份状态
cd ~/Molin-OS && \
  git stash && \
  git pull && \
  cp ~/.hermes/backups/env/latest.env .env && \
  chmod 600 .env && \
  bash scripts/deploy.sh && \
  make restart && \
  make health
```

## 九、风险记录

| 风险 | 概率 | 影响 | 触发条件 | 缓解措施 |
|------|------|------|---------|---------|
| **全新安装失败**（某依赖无法在 macOS 15 上编译） | 低 | 高（延迟 2h+ 安装） | macOS 大版本升级后 Homebrew 兼容性问题 | deploy.sh 3a 步可检测；降级方案为手动 `brew install` |
| **升级导致配置不兼容**（新环境变量字段未定义） | 中 | 中（Agent 功能降级） | `git pull` 后 `.env.example` 新增必填变量 | deploy.sh 3g 步做 schema 校验，缺失项打印警告 |
| **轮换密钥泄露**（90 天内被截获） | 极低 | 极高（API 被滥用） | `.env` 权限被修改 / 被恶意进程读取 | `.env` 权限 600 + 日志审计 `stat .env` |
| **硬件故障**（硬盘损坏 / 内存失效率） | 低 | 极高（全系统不可用） | 物理硬件寿命终结 | 备有"第二台 MacBook"恢复计划（见 9.1） |
| **GitHub 宕机** | 极低 | 中（备份失败） | GitHub 服务故障 | 本地备份保留 7 日，Gitee 镜像可作二级备份 |

### 9.1 全新安装 vs. 升级路径

| 场景 | 步骤 | 时长 | 成功概率 |
|------|------|------|---------|
| **全新安装**（从未部署过的机器） | `git clone → deploy.sh → make start → make health` | ≈18 分钟 | >95%（最近 3/3 次成功） |
| **升级安装**（已有部署，`git pull`） | `git pull → deploy.sh → make restart → make health` | ≈5 分钟 | >98%（依赖未变更时约 30 秒） |
| **跨版本升级**（3 个月以上未更新） | `git pull → deploy.sh (可能需处理 breaking changes) → make restart → make health` | ≈15 分钟 | >90%（需手动处理 1–2 个配置项） |

### 9.2 回滚流程

当升级导致系统不稳定时，按以下步骤回滚：

```bash
# 标准回滚（保留 .env）
cd ~/Molin-OS
git reflog                      # 查看历史提交记录
git reset --hard HEAD@{1}       # 回滚到上一个版本
bash scripts/deploy.sh          # 重新部署旧版本
make restart
make health

# 紧急回滚（还原到最近一次 make backup 的备份）
git stash                       # 保存当前未提交修改
git checkout $(git log --oneline --all | grep "backup" | head -1 | awk '{print $1}')
bash scripts/deploy.sh
make restart
make health
```

**回滚成功标准：** `make health` 六项检查全部通过。若回滚后仍不稳定，执行完整恢复流程（见 8.3 节）。
