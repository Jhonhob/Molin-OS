# 元瑶教育Agent项目总计划

---

## 0. SCQA：为什么学员记忆是第一步

**Situation（情境）**：元瑶已经上线飞书机器人教育频道，学员每天来问数学/英语/编程题目，每节课40分钟，对话式教学。

**Complication（冲突）**：学员每次开启新会话都是"陌生人"——系统不记得ta上周卡在哪道题，薄弱点是什么，上次推荐的练习做了没。学员被迫每次重新自我介绍（"我几何不太好""我上次学到二次函数了"），教学效率被重复信息消耗，学习连续性断裂。无记忆 = 无个性化 = 和搜索引擎没区别。

**Question（问题）**：如何在**零开发成本、零额外登录**的前提下，让系统在下一次会话中自动认出学员、恢复上下文、实现"老师记得我"的体验？

**Answer（答案）**：以飞书 **open_id** 为零成本身份锚点，复用已有 **Obsidian** 记忆架构（原Supermemory已停用），完成最小闭环。后续演进为多Agent教育系统（诊断/教学/督学三Agent联动）。

---

## 1. 学员记忆MVP方案

复用已有Obsidian单通道架构（原Supermemory已停用），以飞书open_id为零成本身份锚点。飞书是现有触点学员身份直接用open_id无需额外登录，FastAPI+Python与现有同步脚本同栈。

## 2. 决策记录（ADR）

### ADR-001：身份锚点选飞书 open_id 而非 WeChat / 手机号

| 选项 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| **飞书 open_id** ✅ | 零成本获取、不要求用户登录、与机器人消息同上下文 | 仅限飞书生态、非通用ID | 当前MVP唯一可行 |
| 微信号 | 通用社交ID | 需额外OAuth授权、学员未必同意绑定 | 优先级低 |
| 手机号 | 强唯一性 | 合规风险（个保法）、需验证码、增加摩擦 | 否决 |

**决定**：飞书 open_id 在 MVP 阶段是唯一合理选择。后续如需打通多端（Web/微信），可在学员画像中建立 open_id ↔ 其他ID 的映射表。

### ADR-002：记忆存储选 Obsidian（原Supermemory已停用）而非自建 DB

| 选项 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| **Obsidian** ✅ | 零维护、可人工审核 | 无向量检索 | 适合MVP（原Supermemory已停用） |
| 自建 PostgreSQL | 强一致性、灵活查询 | 需部署+维护+迁移现有数据 | 太重，否决 |
| Redis | 极低延迟 | 无持久化保证、不适合JSON文档 | 仅可做缓存 |

**决定**：MVP 阶段直接复用。若后续 QPS > 10 或需要事务性写入，再考虑叠加 Redis 缓存层 + PostgreSQL 持久层。

### 关键时序说明

- **步骤③查询**：必须在 LLM 推理前完成，否则注入延迟会造成学员等待
- **步骤④缓存**：Supermemory（已停用）返回的 profile 应缓存在中间件内存中（10分钟TTL），避免同学员短时间多次查询
- **步骤⑨保存**：每次会话结束时异步保存；长会话（>10轮）可在中途做一次阶段性保存防丢

## 5. 三会话剧本："系统记得我"体验

### 会话一：Day 1 — 首次接触

```
学员：在吗？我想学二次函数
元瑶：欢迎小雨！第一次来，我们先聊聊你现在的水平？你学过一次函数和一元二次方程吗？
学员：学过，但方程解不太好……
（40分钟教学后）
元瑶：今天我们学了二次函数顶点式，你配方法还有点生疏。下次我给你准备5道配方法练习题，我们接着学～
```

**系统动作**：创建新 session，Supermemory（已停用）无历史记录 → 教学后首次保存。

---

### 会话二：Day 2 — 被记住

```
学员：来继续吧
元瑶：【Profile注入】小雨来啦！上次我们学了二次函数顶点式，你说配方法有点难。我准备了5道题，我们先热个身？
学员：哇你还记得！！（惊喜）
（40分钟教学，正确率80%）
元瑶：进步很大！配方法基本过关了。下次我们学二次函数与一元二次方程的关系，预习一下零点的概念哦～
```

**系统动作**：
1. Supermemory（已停用）查到 open_id → 返回 `last_session_summary`
2. System Prompt 注入："学员小雨，上次2026-04-10学二次函数顶点式（session_001），困难点是配方法转化为顶点式。上次结束时留了5道配方法练习题。今天重点：先检查作业再做新内容。"
3. 学员感受到"被记住" → 建立信任
4. 会话结束时追加 session_002

---

### 会话三：Day 3 — 累积洞察

```
学员：我昨晚做了上次的题，对称轴那个推导没懂
元瑶：【Profile注入】好的！上次我们学了零点，你说求根公式负号容易错、对称轴推导不理解。今天我们从对称轴推导讲起，然后做含参零点讨论，你看行吗？
学员：好！正好是我卡住的地方……
```

**系统动作**：
1. Supermemory（已停用）查到连续两次 session 的 `pain_points` 交集
2. 自动发现：学员对代数运算推导类内容持续薄弱
3. System Prompt 额外注入：**"该学员连续3次会话均在代数推导环节遇到困难（配方法→对称轴→求根公式），建议今天优先强化代数推导基本功，降低概念讲解比例。"**
4. 教学策略动态调整：从"讲新概念"切换到"练基本功"

**学员感受**：系统不仅记得上次说了什么，**还能发现我的规律性困难**，教学优先级有针对性。

## 6. 验证指标（基线 vs 目标）

| 指标 | 基线（无记忆） | 目标（MVP上线4周） | 测量方式 |
|------|---------------|-------------------|----------|
| 学员第二次会话率 | ≤25%（推测） | **≥60%** | 飞书机器人日志：open_id 出现≥2个不同日期 |
| 被记住正向反馈率 | — | **≥70%** | 会话结束后弹出一键评价："系统记得你上次的内容吗？"（是/否） |
| 每周人均会话频次 | ≤1次（推测） | **≥2次** | 周聚合：会话数/去重学员数 |
| 学员首次引入旧知识时间 | 会话开始后~5分钟 | **≤30秒** | 从首条消息到系统提及上次学习内容的时间差 |
| 教学效率（概念掌握/会话轮数） | 低（重复消耗） | **提升≥30%** | 同难度题目首次正确率 vs 基线 |

### 指标采集方案

- 二次会话率：飞书 open_id 维度的日活去重统计
- 被记住反馈：每会话结束时用飞书消息卡片发一个 2 按钮（是/否）投票
- 轮数/正确率：从 session JSON 中聚合计算

## 7. 风险与缓解

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|----------|
| **open_id 冲突**（极少，但飞书不同租户可能生成相同open_id？飞书设计上open_id租户内唯一，跨租户无冲突场景。除非我们自己混用多个飞书应用。） | 低 | 高 | 在中间件层叠加 `tenant_key + open_id` 复合主键 |
| **Supermemory写入延迟 > 500ms（已停用）**导致会话结束前的save卡住 | 中 | 中 | 写操作用异步任务（Celery / asyncio.create_task），不阻塞主对话流程 |
| **Supermemory查询失败/超时（已停用）**导致注入失败 | 中 | 高 | 降级策略：查询失败时以空上下文继续教学，不阻断对话；同时告警 |
| **飞书 API 频率限制**（消息发送+消息卡片回调） | 中 | 中 | 加入令牌桶限流，日志监控接近限值预警 |
| **长会话中途掉线**导致未保存session丢失 | 中 | 中 | 每10轮对话或每5分钟自动执行一次阶段性保存（upsert到Supermemory（已停用）) |
| **学员隐私合规**：Supermemory存储位置未知（已停用），可能违反个保法 | 低 | 高 | Obsidian 副本存本地；确认 Supermemory（已停用）数据驻留区域；学员可请求删除 |

## 8. 多Agent扩展计划（诊断/教学/督学）

### 8.1 终极架构

```
                      ┌─────────────────────────────────────┐
                      │           记忆中台 (Memory)           │
                      │  Obsidian 作为共享记忆（原Supermemory已停用）   │
                      └──────┬──────────┬──────────┬────────┘
                             │          │          │
              ┌──────────────┼──────────┼──────────┼──────────────┐
              │              │          │          │              │
         ┌────▼────┐  ┌─────▼─────┐  ┌─▼──────────▼─┐  ┌───────▼──────┐
         │ 诊断Agent │  │ 教学Agent  │  │  督学Agent    │  │ 元(仲裁Agent) │
         │ (D)      │  │ (T)       │  │ (S)          │  │ (Coordinator) │
         └────┬────┘  └─────┬─────┘  └──────┬───────┘  └───────┬──────┘

              └─────────────┼───────────────┼──────────────────┘

```

### 8.2 各Agent职责

| Agent | 角色 | 核心能力 | 触发条件 |
|-------|------|----------|----------|
| **诊断 Agent (D)** | 学习分析师 | 分析 session 历史 → 生成知识点掌握矩阵 → 输出「薄弱点TOP3 + 推荐学习路径」| 新学员首次会话 / 每5次会话后复盘 / 学员主动请求"帮我诊断一下" |
| **教学 Agent (T)** | 授课教师 | 根据诊断结果+当前目标 → 定制化讲解+出题+批改 | 学员日常对话、提问 |
| **督学 Agent (S)** | 学习教练 | 跟踪进度 → 催作业 → 心理激励 → 提醒复习时间窗口（艾宾浩斯曲线） | 每日定时 / 学员长时间未出现 / 关键复习窗口 |
| **元 Agent** | 仲裁调度 | 路由学员消息到对应Agent → 管理Agent间上下文传递 → 解决Agent间冲突（如T想讲新内容但S认为该复习） | 每一条学员消息 |

### 8.3 多Agent协作流程示例

```
Day 1: 学员首次来 → D诊断Agent生成基线画像（代数3/10分，几何5/10分）
Day 1-5: T教学Agent按D推荐路径讲代数 → 每节课追加session
Day 5: S督学Agent检测到学员连续2天未出现 → 发飞书消息："小雨，代数基本不等式还没讲完哦，今晚有空来吗？"
Day 10: D诊断Agent重新评估 → 代数7/10分 → 建议切换几何 + 代数周期性复习
Day 10+: T切换教学重心到几何，但每3天穿插一道代数综合题（S的间隔复习策略）
```

### 8.4 MVP → 多Agent演进路径

| 阶段 | 时间 | 目标 | 关键动作 |
|------|------|------|----------|
| **P0（当前）** | Week 1-3 | 单人记忆MVP | 记忆中间件 + 飞书触点 + 被记住体验 |
| **P1** | Month 2 | 诊断Agent上线 | 基于session历史自动生成薄弱点分析 + 推荐路径，T Agent依赖诊断输出 |
| **P2** | Month 3 | 教学Agent独立 | T Agent按诊断结果动态调整教学内容，减少人工规则，引入RAG教材库 |
| **P3** | Month 4 | 督学Agent上线 | 定时任务 + 飞书主动消息 → 督学催复习/催作业 |
| **P4** | Month 5-6 | 元Agent + 群聊 | 多Agent协同调度，支持群聊教学场景（#数学教室群），学员之间可互看（可选） |
