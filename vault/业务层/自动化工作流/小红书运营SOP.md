# 小红书运营标准作业程序（SOP）

## 1. SCQA 背景：为什么需要这套 SOP

- **Situation（现状）**：小红书日活突破 3 亿，笔记生命周期极短（黄金窗口约 2–6 小时）。手动逐一检查笔记互动变化、手动回复评论、手动追踪竞品动态，已完全不可持续。
- **Complication（矛盾）**：多账号运营、评论量激增、平台算法频繁调整（2025–2026 年已三次改版推荐权重），纯人工模式导致回复超时率 > 40%，互动转化率逐月下滑。
- **Question（问题）**：如何建立一套可自动执行、可监控、可迭代的标准化运营流程，覆盖从内容发布 → 数据监控 → 用户回复 → 竞品分析的全链路？
- **Answer（方案）**：本 SOP 以 **每小时自动化监控管道** 为核心，配合结构化提示词工程、六域分类回复决策、竞品调研流水线，实现运营的工业化、数据化、闭环化。

## 2. 决策记录（Architecture Decision Records）

### ADR-001：为什么采用每小时监控而非实时/每日

| 维度 | 实时监控 | 每小时监控（选定） | 每日监控 |
|------|----------|-------------------|----------|
| API 调用成本 | 极高，易触发频率限制 | **中等，可控** | 低 |
| 互动响应时效 | < 1 min | **≤ 60 min** | 24 h |
| 平台风控风险 | 高（疑似爬虫） | **低** | 低 |
| 数据密度 | 冗余噪声多 | **足够用于趋势分析** | 粒度太粗 |
| 运维复杂度 | 高（需高可用架构） | **中等** | 低 |

**结论**：每小时监控在 **响应时效** 与 **成本/风险** 之间取得最优平衡，60 分钟内响应评论可覆盖约 85% 的用户期待时效。

### ADR-002：为什么封面提示词使用结构化 JSON 而非纯文本描述

| 维度 | 纯文本提示词 | 结构化 JSON（选定） |
|------|-------------|-------------------|
| 元素可控性 | 模糊，模型自由发散 | **每个字段精确控制** |
| 批量复用 | 每次需重写 | **字段模板化，参数化调用** |
| 版本对比 | 无法结构 diff | **字段级 diff，精准迭代** |
| 否定约束能力 | 弱，"不要 XX" 常被忽略 | **独立 `negative_constraint` 字段，效果显著** |
| 测试覆盖率 | 凭感觉 | **可自动化字段组合测试** |

**结论**：结构化 JSON 四层范式将封面生成从「抽卡」变为「工程」，工业级复用。

## 3. 笔记监控管道（Monitoring Pipeline）

### 3.1 管道拓扑

```
[发布适配器] → [排队队列] → [xiaohongshu-monitor-1h] → [状态变化缓冲区]
      ↑                                                           ↓
      └──────────────────── [飞书告警中心] ←── [会话管理服务] ←────┘
                                       ↑
                              [错误恢复模块]
```

### 3.2 每小时监控步骤（详细流程）

1. **会话验证**：检查 `X-RED-TOKEN` 与 `Cookie` 是否有效。若失效 → 进入错误恢复流程（见 §7）。
2. **数据拉取**：请求笔记详情 API（`/api/notes/{id}`），获取互动指标：
   - `likes` / `collections` / `comments` / `shares`
   - `impression` 曝光量（如有权限）
3. **增量对比**：对比上一小时快照，计算：
   - `Δ_likes` `Δ_collections` `Δ_comments` `Δ_shares`
   - `growth_rate` = (当前值 - 上一小时值) / 上一小时值
4. **异常检测**：
   - 若 `Δ_comments > 50` 且为负 → 标记【疑似删除/折叠】
   - 若 `growth_rate > 300%` → 标记【爆款预警】
   - 若连续 4 小时 `Δ ≈ 0` → 标记【停滞，建议优化标题/封面】
5. **数据写入**：记录到时序数据库（保留 30 天滚动窗口）。
6. **结果推送**：状态变化通过飞书 Bot Webhook 推送至专用频道。

### 3.3 典型互动指标参考

| 笔记类型 | 1h 基准互动量 | 爆款阈值（发布后 6h） | 衰退窗口 |
|----------|-------------|---------------------|---------|
| 图文教程 | 50–150 | > 3000 | 12–24 h |
| 穿搭展示 | 80–200 | > 5000 | 8–16 h |
| 测评对比 | 30–100 | > 2000 | 24–48 h |
| 热点话题 | 200–800 | > 15000 | 2–6 h（短命爆款） |

## 4. 封面提示词工程（Prompt Engineering）

### 4.1 结构化 JSON 范式（GPT Image 2 专用）

```json
{
  "subject": {
    "type": "人物 | 产品 | 场景",
    "description": "日系通勤穿搭，女性，25-30岁",
    "attributes": ["米色风衣", "阔腿裤", "帆布包"]
  },
  "environment": {
    "setting": "城市街角咖啡店外立面",
    "lighting": "自然光+暖色调路灯补光",
    "time_of_day": "傍晚蓝调时段"
  },
  "action_state": {
    "pose": "侧身回眸，手持咖啡杯",
    "expression": "自然微笑，眼神柔和",
    "moment": "走路被叫住回头瞬间"
  },
  "style_and_medium": {
    "art_style": "写实偏胶片质感",
    "color_palette": "暖棕+奶咖+浅灰",
    "camera": "35mm, f/1.8, 浅景深"
  },
  "lighting_bank": "轮廓光 + 眼神光 + 环境漫反射",
  "quality_suffix": "4k, highly detailed, commercial photography",
  "negative_constraint": "手部畸形, 过多细节模糊, 过度磨皮, 卡通化, 脸部不对称"
}
```

### 4.2 字段设计原理

- **主体+环境+动作状态+风格媒介**（四层结构）：各层独立变化，按 SKU 矩阵排列可批量生产百张不同封面。
- **光照词块**：统一置于 `lighting_bank`，避免各层语义冲突导致光源错乱。
- **质量尾缀**：`quality_suffix` 和 `negative_constraint` 独立字段，不干扰主体描述，确保质量参数被模型优先处理。

## 5. 回复决策系统（Reply Classification）

### 5.1 六域分类表

| 领域 | 关键词（正则/词库） | 回复策略 | 优先级 | 期望响应时间 | 自动化率目标 |
|------|-------------------|---------|--------|------------|------------|
| 产品咨询 | `多少钱`, `哪里买`, `链接`, `型号`, `价格` | 标准话术 + 商品卡链接 | P0 | ≤ 15 min | 90% |
| 使用疑问 | `怎么用`, `步骤`, `教程`, `效果`, `合适吗` | 详细解答 + 引导收藏笔记 | P1 | ≤ 30 min | 80% |
| 负面反馈 | `不好用`, `差评`, `退了`, `踩雷`, `智商税` | 私信处理；公开回复安抚+说明改进 | P0 | ≤ 10 min | 60%（需人工复核） |
| 社交互动 | `好看`, `可爱`, `厉害`, `不错`, `赞` | 感谢 + 互动钩子（提问引导再评论） | P2 | ≤ 60 min | 95% |
| 抄袭/侵权 | `抄的`, `盗图`, `侵权`, `举报` | 拉高声援回复 + 保留证据截图；触发法务流程 | P0 | ≤ 5 min | 40%（高风险，必须人工确认） |
| 垃圾/广告 | `加微`, `代购`, `私聊`, `tg`, `wx` | 直接删除 + 拉黑；飞书告警通知运营 | P0 | ≤ 5 min | 95% |

### 5.2 回复决策流程

```
评论进入 → 六域分类器（关键词匹配 + 轻量 NLU）
    ↓
[P0 类] → 自动回复/删除 ← 若置信度 < 0.85 → 标记待人工
[P1 类] → 自动回复 + 笔记内嵌引导
[P2 类] → 自动回复  ← 若当日互动 > N 条 → 随机化话术避免模板感
    ↓
每日 08:00 汇总 → 输出情报简报（分类分布 + 各分类互动率 + 话术点击率）
```

### 5.3 分类准确度目标

| 指标 | 当前基线 | 目标值 | 测量方式 |
|------|---------|--------|---------|
| 分类准确率 | 82% | ≥ 92% | 每周人工抽查 200 条 |
| P0 类召回率 | 71% | ≥ 95% | 追踪漏标后被用户投诉的数量 |
| 自动回复采纳率 | 不回复时 N/A | ≥ 75% | 用户二次回复率 |

## 7. 错误恢复（Error Recovery）

### 7.1 会话过期恢复 SOP

```
触发条件：API 返回 401 / 403 / {"code": 10003}
   ↓
1. 立即暂停该账号所有监控任务 ← 避免重复 401 刷屏
2. 发送飞书告警 T4（含账号名 + 失败时间 + 最后成功快照）
3. 等待运营手动刷新 Cookie/Token
   ↓
   若 30 分钟内未完成刷新 → 升级为 T3 告警（@oncall 值班人员）
   ↓
   若 2 小时内未恢复 → 判定为账号异常，转入账号健康检查流程
   ↓
4. 刷新成功后 → 自动恢复监控管道（从上次成功快照继续，不重新拉取）
```

### 7.2 API 速率限制处理

```
触发条件：429 / {"code": 10020, "msg": "请求过于频繁"}
   ↓
1. 当前管道立即退避：sleep(base_delay * 2^retry_count)
   - base_delay = 60s, max_delay = 1800s
2. 记录 rate_limit_hit 到运维指标
3. 若 12h 内 rate_limit_hit > 5 次 → 自动降低该账号管道频率
   （1h → 2h 轮询间隔）
4. 降低后 24h 内未再触发 → 恢复 1h 轮询
```

### 7.3 平台反爬/封号场景

| 场景 | 检测信号 | 自动措施 | 手动措施 |
|------|---------|---------|---------|
| IP 被限制 | 所有 API 返回网络错误 | 切换代理 IP 池（自带 5 个住宅代理） | 更换云厂商地域 |
| 账号被限流 | 曝光量骤降 80%+，无异常码 | 暂停发布 48h，降低监控频率至 4h | 向平台申诉，备号切换 |
| 账号被封禁 | 登录接口返回 code=20002 | 立即停用账号，迁移数据 | 法人认证申诉/弃号 |
| 设备指纹识别 | 同一 UA 大量请求被拦截 | 轮换 UA + 请求间隔随机化（±30s jitter） | 更换设备参数指纹 |

## 8. 任务调度表（Scheduling）

### 8.1 定时任务一览

| 任务名称 | 描述 | 执行策略 | Cron 表达式 | 期望执行耗时 | 依赖 |
|---------|------|---------|------------|------------|------|
| `xh-monitor-1h` | 笔记互动监控 | 每小时轮询所有活跃笔记 | `0 * * * *` | < 30s / 100 篇 | 会话有效 |
| `xh-reply-classify` | 未回复评论分类与自动回复 | 每 15 分钟 | `*/15 * * * *` | < 10s | — |
| `xh-daily-digest` | 每日运营情报简报生成 | 每日 08:00 | `0 8 * * *` | < 60s | 前一日完整数据 |
| `xh-cover-batch` | 封面素材批量预生成 | 每周一 04:00 | `0 4 * * 1` | 5–15 min | OpenAI API 配额充足 |
| `xh-comp-weekly` | 竞品周度分析报告 | 每周一 07:00 | `0 7 * * 1` | 5–10 min | 竞品名单有效 |
| `xh-session-refresh` | 会话 Token 健康检查 | 每 30 分钟 | `*/30 * * * *` | < 5s | — |
| `xh-data-archive` | 30 天前数据归档至冷存储 | 每日 02:00 | `0 2 * * *` | < 30s | — |

### 8.2 调度约束

- 同一账号的 `monitor-1h` 与 `reply-classify` 不得同时执行（通过分布式锁实现），避免请求突发。
- 所有定时任务统一由内部调度器管理，支持 **手动触发** 和 **跳过执行**（用于维护窗口）。

## 9. 风险与应对（Risk & Mitigation）

| 风险类别 | 具体风险 | 影响等级 | 发生概率 | 应对措施 |
|---------|---------|---------|---------|---------|
| 平台策略 | 推荐算法调整导致流量腰斩 | 🔴 高 | 中 | 多平台分发 + 至少保留 3 个月的互动数据做归因分析 |
| 账号安全 | 批量封号/限流 | 🔴 高 | 中 | 主备账号 1:2 配置，日常负载分散，关键操作仅主账号执行 |
| 技术风险 | 第三方 API 不可用（如 OpenAI） | 🟡 中 | 低 | 封面生成备选模型（Claude/Gemini），降级为文本提示 |
| 数据风险 | 互动数据丢失或损坏 | 🟡 中 | 低 | 每半小时增量备份 + 每日全量备份至独立存储 |
| 合规风险 | 自动回复违规词导致笔记限流 | 🟡 中 | 中 | 回复前过敏感词库 + 人工复核 P0 负面类 |
| 运维风险 | 凌晨管道故障无人响应 | 🟢 低 | 低 | 飞书告警升级机制：T4(即时) → T3(30min) → T2(2h,@值班手机) |
