## SCQA开场：中继机制的存在理由

**Situation（情境）**：墨麟OS的内容飞轮每日产出多篇自动化内容并分发至各平台，但内容效果数据（浏览/点赞/收藏/分享/转化）散落在各平台，未被系统性地回收利用。

**Complication（冲突）**：没有反馈回路的内容飞轮是开环系统——选题预测是否准确？标题公式是否有效？平台分发策略是否最优？这些问题随时间累积，内容质量会退化而非进化。

**Question（问题）**：如何设计一个可重复的闭环机制，让每日内容表现数据自动流回情报层和技能库，驱动选题模型、标题策略、平台分发方案持续迭代？

**Answer（答案）**：Agent中继机制（Relay）——每日11:00自动执行的数据回收与注入管道，将「执行端」的内容表现反馈回「策略端」的情报层和技能库，形成完整的PDCA飞轮闭环（P-情报计划 → D-内容执行 → C-中继检查 → A-技能调整）。

---

## 决策记录：为何选择11:00

| 维度 | 备选时间 | 评估 | 结论 |
|------|----------|------|------|
| **数据完备性** | 08:00（与情报管道并线） | 增长引擎10:45才完成数据写入，08:00无数据可用 | ❌ |
| **管线时序对齐** | 12:00 / 14:00 | 滞后1-2小时不影响本日产出，但延迟注入影响次日08:00情报采集 | ⚠️ 可接受但非最优 |
| **次日链路衔接** | **11:00（当前选择）** | 增长引擎10:45写入完毕，留15分钟缓冲；分析结果可被次日08:00情报管道读取，刚好赶上次日全链路 | ✅ 最优 |
| **峰谷负载** | 11:00 | 避开了08:00情报采集、09:20内容工厂、10:45增长引擎的执行高峰，系统负载均衡 | ✅ |

**决策结论**：11:00是唯一在「当日数据可获取性」与「次日链路可用性」之间取得平衡的时间窗口。

## 执行流程（详细分步）

### 步骤一：数据源确认（Plan → Check 过渡）

**目标**：确保relay/intelligence.json存在且包含有效的当日采集数据。

**子步骤**：
1. **路径解析**：读取 `relay/intelligence.json`（约定路径，由情报管道在08:00写入）
2. **完整性验证**：校验JSON结构是否符合Schema（见下文）
3. **新鲜度检查**：确认数据采集时间戳为当日（`collection_timestamp` >= 当日00:00:00 UTC+8）
4. **最小数据量检查**：至少存在1条有效的已发布内容记录（`published_items.length >= 1`）

**决策点**：
- 若文件不存在 → 进入**错误处理流程A**（见后文）
- 若文件存在但数据为空/格式错误 → 进入**错误处理流程B**
- 若文件存在且数据有效 → 继续步骤二

**成功标准**：`relay/intelligence.json` 校验通过，数据新鲜度与数量符合要求。

---

### 步骤二：数据回收与分析（Check 阶段）

**目标**：拉取已发布内容的互动数据，计算表现指标，对比情报层预测与实际表现。

**子步骤**：
1. **内容数据拉取**：从intelligence.json提取 `published_items` 列表，获取每条内容的：
   - `content_id`（内容唯一标识）
   - `platform`（发布平台：小红书/抖音/B站/公众号）
   - `published_at`（发布时间戳）
   - `predicted_metrics`（情报层预测值：predicted_views / predicted_engagement_rate）
2. **互动数据聚合**：统计每条内容的实际表现：
   - `real_views`（实际浏览量）
   - `real_likes`（实际点赞数）
   - `real_comments`（实际评论数）
   - `real_favorites`（实际收藏数）
   - `real_shares`（实际分享数）
   - `real_conversions`（实际转化数，如有）
3. **指标计算**：
   - `engagement_rate = (likes + comments + favorites + shares) / views × 100%`
   - `conversion_rate = conversions / views × 100%`
   - `prediction_accuracy = 1 - |predicted - real| / predicted`（浏览量维度）
   - `platform_distribution`：按平台聚合各项指标
4. **对比分析**：
   - 逐条对比情报层预测 vs 实际表现，标记偏差 >20% 的内容为「预测异常」
   - 识别表现最优的3条内容（按互动率排序），提取其标题公式、选题方向、平台特征

**输出 Schema**（写入 `relay/analysis.json`）：

```json
{
  "relay_id": "relay-2026-05-19",
  "execution_timestamp": "2026-05-19T11:01:30+08:00",
  "data_period": {
    "start": "2026-05-18T11:00:00+08:00",
    "end": "2026-05-19T11:00:00+08:00"
  },
  "summary": {
    "total_items_analyzed": 12,
    "platforms_covered": ["小红书", "抖音", "B站"],
    "avg_engagement_rate": 5.23,
    "avg_prediction_accuracy": 0.78
  },
  "per_item": [
    {
      "content_id": "content-20260519-001",
      "platform": "小红书",
      "title": "示例标题",
      "predicted_views": 5000,
      "real_views": 7234,
      "prediction_accuracy": 0.69,
      "engagement_rate": 8.12,
      "insight_generated": "标题含'数字+痛点'模式的互动率比均值高60%"
    }
  ],
  "top_performers": [
    {
      "content_id": "content-20260519-003",
      "platform": "抖音",
      "engagement_rate": 12.45,
      "title_formula": "反问句式 + 视觉冲突",
      "key_pattern": "前3秒钩子+冲突陈述"
    }

    "抖音": { "avg_engagement": 4.8, "best_post_type": "冲突剪辑" },

```

**决策点**：
- 若分析结果为空（无任何内容可分析）→ 记录警告，跳过步骤三
- 若只有单一平台有数据 → 标记为「部分数据」，继续分析但降低置信度

**成功标准**：`relay/analysis.json` 成功生成，包含至少3个维度的分析结果（互动率/预测准确率/平台特征）。

---

### 步骤三：技能库更新（Act 阶段）

**目标**：基于分析结果识别需要更新的技能文件，将新的行为模式、标题公式、平台洞察注入技能库。

**子步骤**：
1. **差异识别**：对比本次analysis.json与历史分析记录（`relay/analysis_history.json`），识别显著变化的指标
2. **技能映射**：根据分析结果确定需要更新的技能文件及注入内容：

| 分析发现 | 目标技能文件 | 更新内容 |
|----------|-------------|----------|
| 某标题公式互动率 > 8% | `skills/content-writing.md` 的 `references.title_formulas` | 追加新标题公式 + 示例 |
| 某平台表现明显优于其他平台 | `skills/platform-strategy.md` 的 `references.platform_weights` | 调整平台权重 / 更新分发策略 |
| 预测偏差 > 30% 的模式 | `skills/intelligence.md` 的 `references.prediction_rules` | 修正预测参数 / 更新热点权重 |
| 竞品内容表现异常 | `skills/competitor-analysis.md` 的 `references.catch_up_strategies` | 更新竞品分析策略 |

3. **技能注入**：将新洞察追加至目标技能的 `references` 区段的末尾，格式为：
   ```
   <!-- relay-2026-05-19 -->
   - [注入点] 标题公式："{公式描述}" — 互动率{value}%，日期：2026-05-19
   ```
4. **版本标记**：在技能文件头部更新 `last_updated` 字段并追加Relay版本记录

**决策点**：
- 若分析结果无明显改进信号（所有指标持平或下降）→ 仅记录存档，不触发技能更新
- 若多个技能文件需要同时更新 → 按优先级排序：内容写作 > 平台策略 > 情报预测 > 竞品分析

**成功标准**：至少1个技能文件被成功更新，更新内容可追溯到本次Relay ID。

## 错误处理

### 流程A：relay/intelligence.json 缺失

| 阶段 | 操作 |
|------|------|
| 检测 | 步骤一超时300ms内未找到文件 |
| 重试 | 间隔30秒重试，最多3次（共90秒） |
| 降级 | 若3次重试后仍缺失，检查备份路径 `relay/archive/intelligence_prev.json`（前一日数据） |
| 使用备份 | 若备份存在 → 使用前日数据执行分析，标记为「降级模式」 |
| 无备份 | 若备份也缺失 → 跳过当日Relay执行，记录紧急日志，通知人工排查 |
| 告警 | Slack通知渠道 `#monitor-agent-relay`，标题「中继缺失：intelligence.json未生成」 |

### 流程B：relay/analysis.json 数据损坏

| 阶段 | 操作 |
|------|------|
| 检测 | JSON解析失败 / 必填字段（published_items）缺失 / 数值超出合理范围（如views=0但likes>0不构成互动率） |
| 修复 | 尝试从原始intelligence.json重建（仅提取原始数据，跳过指标计算） |
| 跳过 | 若intelligence.json也不完整 → 跳过当日Relay |
| 告警 | 同流程A告警渠道，标题「中继异常：analysis数据损坏」 |

### 流程C：技能文件写入冲突

| 阶段 | 操作 |
|------|------|
| 检测 | 同一技能文件在10分钟内被多个并发写入请求锁定 |
| 策略 | 队列化写入，按relay_id排序，后到的等待前一次写入完成（最长等待10秒） |
| 冲突解决 | 若10秒后锁仍未释放 → 跳过该技能文件的本次更新，记录到 `relay/conflicts.json` |
| 人工审核 | 每周汇总conflicts.json发送至 `#review-agent-relay` 供人工判断 |

## PDCA映射

| 执行步骤 | PDCA阶段 | 对应内容 |
|----------|----------|----------|
| 情报管道 08:00 → intelligence.json | **Plan** | 选题预测、热点分析、竞争格局评估 |
| 内容工厂 09:20 | **Do** | 消费情报产出内容并分发 |
| **中继步骤一**：数据源确认 | **Check**（前提） | 确认执行数据可获取，为检查做准备 |
| **中继步骤二**：数据回收与分析 | **Check**（核心） | 检查内容实际表现，对比预测 vs 实际 |
| **中继步骤三**：技能库更新 | **Act**（调整） | 基于检查结果调整策略与技能 |
| 次日情报管道 08:00 | **Plan**（优化后） | 读取Relay注入的洞察，优化预测模型 |

每完成一个Relay周期 = 一次完整的PDCA闭环。闭环频次：每日1次。

## Agent同步协议：下游Agent如何消费Relay产出

### 1. 同步时机

| Agent | 读取Relay产出的时机 | 读取内容 |
|-------|---------------------|----------|
| 情报管道（08:00） | 每日启动时 | `relay/analysis.json` 中的预测修正参数和平台权重调整 |
| 内容工厂（09:20） | 每日启动时 | 技能库中的新注入（标题公式/行为模式），由技能文件直接消费 |
| 增长引擎（10:45） | 每日启动时 | `relay/analysis.json` 中的平台表现分析，优化分发权重 |

### 2. 同步协议格式

下游Agent通过以下约定消费Relay产出：

```
# 约定一：直接文件读取
- relay/analysis.json → 结构化分析数据
- relay/analysis_history.json → 历史趋势数据（用于趋势比对）
- relay/conflicts.json → 写入冲突记录（仅当冲突发生时存在）

# 约定二：技能文件注入
- skills/*.md → 通过 `<!-- relay-YYYY-MM-DD -->` 注释标记识别最新的注入点
- 下游Agent读取技能文件时，扫描最新的 `relay-` 注释标记获取最新洞察

# 约定三：同步状态检查
- relay/.sync_status → 记录最后一次成功同步的relay_id和时间戳
- 下游Agent检查此文件确定当前数据是否为最新
```

### 3. 同步失败处理

| 状况 | 下游Agent行为 |
|------|--------------|
| relay/analysis.json 不存在（Relay未执行） | 使用前次分析数据（如有缓存），标记为「数据滞后」 |
| relay/analysis.json 存在但版本号过低 | 从最小版本向前增量消费 |
| 技能文件锁定中 | 等待最多5秒后重试，超时则跳过本次同步，记录到agent本地日志 |

## 风险登记

### 风险1：分析数据被损坏或篡改

| 维度 | 描述 |
|------|------|
| 可能性 | 低（每日1次写入，攻击面小） |
| 影响 | 高（错误的分析结果会导致技能库被注入错误模式，恶化内容质量） |
| 缓解措施 | 1. 写入前校验JSON Schema 2. 写入后立即校验数字范围（如互动率 0%~100%）3. 保留前次analysis.json作为回滚点 4. 超出阈值（如互动率 > 50%）自动触发人工审核 |
| 恢复流程 | 从 `relay/archive/analysis_prev.json` 回滚，重新执行Relay（需人工确认）、 |

### 风险2：技能注入冲突

| 维度 | 描述 |
|------|------|
| 可能性 | 中（随技能文件数量增长而升高） |
| 影响 | 中（可能导致技能文件格式损坏或内容重复） |
| 缓解措施 | 1. 队列化写入机制 2. 每次注入使用统一注释标记（`<!-- relay-YYYY-MM-DD -->`）确保可逆 3. 每日写入前备份技能文件快照 |
| 恢复流程 | 从 `.bak` 快照恢复，重新执行Relay |

### 风险3：管家升级影响

| 维度 | 描述 |
|------|------|
| 可能性 | 中（每次墨麟OS升级或技能库重建时可能影响路径约定） |
| 影响 | 高（Relay依赖的relay/路径或技能库路径变动会导致整个机制失效） |
| 缓解措施 | 1. 将路径配置抽离为 `config/relay_paths.json` 2. 各Agent通过配置文件而非硬编码路径寻址 3. 每次升级后执行Relay自检流程 |
| 恢复流程 | 更新 `config/relay_paths.json` 中的路径配置，无需修改Relay代码 |

## 与其他管线协作

```
时间线：
08:00 ── 情报管道 ───────────→ intelligence.json
09:20 ── 内容工厂 ── 消费情报 ─→ 产出内容
10:45 ── 增长引擎 ── 分发内容 ─→ 追踪数据
11:00 ── Relay(本SOP) ── 回收数据 ─→ analysis.json + 技能注入
08:00(次日) ── 情报管道(优化后) ── 读取Relay产出
```

**反馈闭环**：Relay产出的分析结果在次日08:00情报采集时被读取，用于：
- 调整热点评分权重 → 更准确的热点预测
- 优化角度推荐算法 → 提升选题与平台匹配度
- 更新竞品分析策略 → 更精准的内容差异化
- 修正标题公式库 → 持续提升点击率和互动率

**版本历史**：
- v1.0 (2026-05-19)：初始版本，覆盖基础三步骤
- v2.0 (2026-05-19)：全面升级，新增SCQA、决策记录、错误处理、具体场景、输出Schema、PDCA映射、Agent同步协议、数据指标、风险登记
