## 1. SCQA：为何技术情报对 Molin-OS 至关重要

### Situation（情境）
Molin-OS 作为玄骨中枢的共享服务层，支撑 AI 内容生成、教育产品、副业工具与出海业务四大域。这些领域的技术栈（LLM 推理、Agent 编排、多模态生成）迭代周期已缩短至 **2-4 周**，行业信息呈指数级增长。团队每天面对的噪音信号远超可处理带宽。

### Complication（挑战）
- **信息滞后风险**：一个关键模型版本更新或竞品功能发布未被及时发现，可能导致 Molin-OS 共享组件（如 Agent 编排层、多模态管道）选用过时方案，浪费 2-4 周工程投入
- **决策碎片化**：各业务线独立跟踪信息，缺乏统一情报中枢，导致重复调研和评估标准不一致
- **信号淹没在噪音中**：Twitter/X、arXiv、GitHub、微信群、RSS 等渠道每日产出数百条 AI 相关资讯，人工筛选成本极高

### Question（核心问题）
如何构建一套 **自动化、量化、可追溯** 的技术情报系统，让 Molin-OS 团队在正确的时间做出正确的技术决策？

### Answer（方案）
建立本文档为**技术调研与评估中心**——一个 Agent 驱动的情报流水线，覆盖情报采集 → 筛选 → 分析 → 决策建议的完整闭环，并以每日简报和每周深度报告两种节奏输出。

## 2. 决策记录（Architecture Decision Records, ADR）

### ADR-001：为什么覆盖这 4 个业务域

| 领域 | 核心理由 | 与 Molin-OS 共享服务层的关联 |
|------|---------|------------------------------|
| **AI 内容** | Molin-OS 最大流量来源，直接依赖 LLM/VLM 生成质量 | 共享推理层、内容安全过滤、多模态管道 |
| **教育** | 用户粘性高，竞品差异需要持续跟踪 | 知识图谱构建、对话式 Tutor Agent |
| **副业** | 商业化引擎，市场趋势驱动产品方向 | 自动化 Agent 工作流、电商数据管道 |
| **出海** | 扩张方向，监管与本地化需求独特 | 多语言 NLP、合规过滤层、跨境支付集成 |

**排除项**：不覆盖底层硬件（GPU/TPU 芯片）、云计算基础设施（AWS/Azure 降价）、企业 SaaS 市场。原因：这些超出 Molin-OS 产品层决策范围，由基础设施团队独立跟踪。

### ADR-002：为什么追踪这 5 类 AI 热点

| 类别 | 选择理由 | 对 Molin-OS 的直接影响 |
|------|---------|------------------------|
| **基础模型** | 模型能力直接决定生成质量上限 | 推理成本、响应速度、支持能力 |
| **Agent 生态** | Molin-OS 核心架构方向 | 编排框架选择、工具调用协议 |
| **监管合规** | 出海业务的生死线 | 内容审核策略、数据跨境方案 |
| **工具链** | 提升团队研发效率 | IDE/CI 集成、自动化测试 |
| **视频多模态** | AI 内容域的新增长点 | 视频生成管道、编辑 API 选型 |

**排除项**：不追踪具身智能（机器人）、自动驾驶、AI 制药。原因：与 Molin-OS 当前业务无直接交集，属于广度扩展而非深度竞争领域。

## 5. 具体场景：一次每日简报的完整追踪

### 场景假设：2026-05-18 的日常情报扫描追踪过程

**MORNING SCAN (06:30 - 07:00) — Agent 自动执行**

```
┌─────────────────────────────────────────────────────────────────┐
│ 06:30 触发 cron job                                            │
│ │                                                              │
│ ├─ RSS 采集（4 域 × 3-5 feeds = ~60 篇文章标题+摘要）           │
│ ├─ GitHub Trending 爬取（Top 25 repos，含 README 首段摘要）     │
│ ├─ Twitter/X 列表扫描（8 个账号 × 最近 10 条推 = ~80 条）      │
│ ├─ arXiv 新提交扫描（cs.CL + cs.CV + cs.AI，过滤 top 10）      │
│ ├─ Product Hunt 昨日新品扫描（含 AI 标签的新产品）              │
│ ├─ 小红书/抖音热度数据采集（3 个关键词 × top 20 = ~60 条）     │
│ └─ 总原始数据量：~200-250 条新闻/帖子                           │
└─────────────────────────────────────────────────────────────────┘
```

**DATA PROCESSING (07:00 - 07:20) — Agent 筛选与分类**

```
┌─────────────────────────────────────────────────────────────────┐
│ 07:00 原始数据进入处理管道                                     │
│ │                                                              │
│ ├─ 去重（同一事件合并，保留最早/最权威来源）                    │
│ ├─ 相关性评分（评分模型：标题+摘要 → 与 Molin-OS 4 域的相关度） │
│ │   - 直接相关（score >= 0.8）：模型更新、竞品发布、政策变化    │
│ │   - 间接相关（0.5 <= score < 0.8）：趋势性讨论、KOL 观点     │
│ │   - 噪音（score < 0.5）：过滤并记录数量（用于统计信噪比）     │
│ ├─ 影响评估（分类到对应业务域 + 标记影响方向：积极/消极/中性） │
│ ├─ 紧急度标记（匹配第 4 节升级触发条件 → 标记为 "ALERT"）      │
│ └─ 输出：精炼后的 ~15-25 条高价值情报条目                       │
└─────────────────────────────────────────────────────────────────┘
```

**SUMMARY GENERATION (07:20 - 07:45) — Agent 撰写简报**

```
┌─────────────────────────────────────────────────────────────────┐
│ 07:20 生成每日竞争简报 Markdown 文件                           │
│ │                                                              │
│ ├─ 标题：Molin-OS 技术简报 2026-05-18                          │
│ ├─ ALERT 区块（如有紧急事件）                                  │
│ ├─ Top Stories (3-5条，含链接+1-2句摘要+影响评估)              │
│ ├─ 按域分类情报列表（AI/教育/副业/出海各 2-5 条）              │
│ ├─ AI 热点更新（5 类中本次扫描到的变化）                       │
│ └─ 行动建议（0-3 条，明确建议：调研/采纳/观望/告警）           │
└─────────────────────────────────────────────────────────────────┘
```

**ACTION RECOMMENDATION (07:45 - 08:00) — 交付与决策**

假设当日扫描发现以下关键信号：

| 信号 | 来源 | 分析 | 建议行动 |
|------|------|------|---------|
| Anthropic 发布 Claude 4 Sonnet，推理能力提升 40% | 官方公告 | 直接影响 Molin-OS 共享推理层选型 | **调研**：安排 2 人日进行 API 对比评估 |
| 某竞品上线 AI 视频生成功能 | Product Hunt | 教育/内容域竞争压力增大 | **告警**：加速视频管道整合优先级 |
| 台湾发布 AI 基本法草案征求意见 | 政府公告 | 出海业务需研读合规影响 | **调研**：法务团队一周内出解读报告 |

交付格式：Markdown -> Slack channel `#tech-intel` + 归档至 Obsidian `简报/` 目录。

## 7. 数据指标与效能跟踪

| 指标 | 当前基线 | 目标值 | 统计方式 |
|------|---------|-------|---------|
| **每周扫描总数据量** | ~1,400 条（日均 ~200 条 × 7） | — | Agent 日志统计 |
| **每周有效情报** | ~140 条（日均 ~20 条） | 信噪比 >15% | 相关性评分 >=0.5 的条目 |
| **每周 ALERT 事件数** | ~5-10 条 | <15 条（过多则阈值过高） | 匹配升级触发条件 |
| **行动建议采纳率** | —（初始化） | >40% | 行动建议条数 ÷ 被实际采纳条数（月度统计） |
| **可量化洞察转化** | —（初始化） | 月度 ≥3 条 | 直接导致技术选型变更/成本节约/风险规避的情报 |
| **平均响应延迟** | —（初始化） | 关键事件 <4 小时 | 事件发生 → 触发 ALERT 通知的时间差 |
| **来源覆盖率** | ~25 个渠道 | 持续扩展 | 独立来源数量（去重后的 RSS/API/社交/搜索渠道） |

**数据收集方式**：每次情报运行结束时，Agent 自动记录扫描量、有效条数、ALERT 数、处理时长。每周深度报告附带统计面板。

## 8. 风险登记册

### R1：信息过载（Information Overload）

| 维度 | 详情 |
|------|------|
| **具体表现** | 渠道扩展导致有效信号占比下降，处理管道压力增大 |
| **严重性** | 高 — 影响所有情报的质量和及时性 |
| **缓解措施** | (1) 相关性评分阈值定期校准（每月复审 top 20 被过滤条目） (2) 新增渠道需试用 2 周并验收信噪比 >10% (3) 每日简报条目数上限为 25 条，超出则自动截断次要条目 |
| **触发恢复** | 当信噪比连续 2 周 <10% 时触发渠道清洗 |

### R2：关键信号遗漏（Key Signal Missed）

| 维度 | 详情 |
|------|------|
| **具体表现** | 某个对 Molin-OS 有重大影响的事件未被及时捕获 |
| **严重性** | 极高 — 可能导致错误的技术决策或错失窗口期 |
| **缓解措施** | (1) 每个域至少 3 个独立信息源作交叉验证 (2) 每周人工抽样 20% 的"被过滤"条目录入 (3) 建立"Missed Signal"回溯机制：被发现遗漏的 signal 即时溯源并补充渠道 (4) 团队任何成员发现遗漏可提 PR/Issue 补充 |
| **触发恢复** | 发现 1 次遗漏即触发渠道补充，记录到复盘文档 |

### R3：数据源失效或降级（Sources Go Dark）

| 维度 | 详情 |
|------|------|
| **具体表现** | RSS feed 停止更新、API key 过期、网站改版、Twitter/X 变更访问策略 |
| **严重性** | 中 — 单一源失效通常可由其他源补位 |
| **缓解措施** | (1) 每个源配置存活检测（连续 3 次扫描无新数据 → 告警） (2) 关键源（如 OpenAI Status）配置冗余备选 (3) 每月 1 次源健康检查巡检 |
| **触发恢复** | 源失效告警发出后 24 小时内人工确认并替换/修复 |

### R4：权限与访问限制（Access Restriction）

| 维度 | 详情 |
|------|------|
| **具体表现** | 某些 API 需要付费订阅、某些信息源被封禁（如 Twitter/X 爬虫限制）、国内网站反爬 |
| **严重性** | 中 |
| **缓解措施** | (1) 优先使用官方 RSS/API（免费为主）(2) 付费渠道需评估 ROI（每月 <$50/源的额度） (3) 对于反爬严格的国内源（如小红书/抖音），使用 Webhook 或第三方数据聚合服务替代直接爬取 |
| **触发恢复** | 访问失败连续 5 次 → 降级到替代方案 → 评估是否付费或更换 |
