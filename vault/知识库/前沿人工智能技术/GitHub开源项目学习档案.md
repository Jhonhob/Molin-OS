## SCQA：为什么需要系统化追踪开源项目

**Situation（情境）**：前沿 AI 技术迭代以月为单位，开源社区是最新实践的第一发源地。每天有成百上千个项目诞生，信息过载是常态。

**Complication（挑战）**：无系统跟踪导致三个问题——（1）重复发现：同一个优质项目被不同 Agent 独立扫描数遍；（2）浅尝辄止：只看 README 不深入源码，学不到架构精髓；（3）落地断层：知道了但没有转化为 Molin-OS 的实际能力。

**Question（问题）**：如何建立一套可复用的开源项目学习管线，从发现到吸收再到风险追踪，让每个项目都不白看？

**Answer（答案）**：本档案就是答案。每一条记录代表一个完整的学习周期——扫描 → 评估 → 源码研读 → 吸收决策 → 技能创建。SCQA 本身也是 Molin-OS 内部评价体系的输出格式。

## 决策记录：项目选择标准

并非所有 Star 高的项目都值得深入。以下是筛选框架：

| 维度 | 权重 | 说明 |
|------|------|------|
| **与 Molin-OS 核心能力的相关性** | 30% | AI Agent、教育系统、知识管理、内容创作 — 直接关联优先 |
| **工程成熟度** | 25% | 有文档、测试、CI/CD、活跃维护，而非概念验证 |
| **架构独特性** | 20% | 是否有 Molin-OS 尚未掌握的架构模式（如 Mesh、MCP、FSRS） |
| **代码质量** | 15% | Go/Python/TypeScript 主栈，模块化程度，可复用性 |
| **社区活跃度** | 10% | Issue 回复及时，PR 被合并，有 Release |

**门槛**：必须是 **生产可用**（≥100★ 且有明确架构价值）或 **架构独特**（即使星数少但模式新颖）。不符合的仅做 brief 浏览，不入档案。

## 项目深度记录

每个项目包含四个维度：学到了什么 → 吸收到墨麟OS了什么 → 明确拒绝了什么 → 风险状态。

### AI Agent 框架

#### TheAgency（200+★）

| 维度 | 内容 |
|------|------|
| **学到** | 226 个 Agent 定义文件的组织结构——每个 Agent 独立文件 + 分层 meta 标签系统，支持 Agent 间引用和继承。Persona 定义的粒度分级（Tier 1-4）是一个优秀的设计模式。 |
| **吸收** | 8 个 Tier 1 Agent 定义已吸收为 SKILL.md。标签分类体系（角色/领域/能力三维）复用到 Molin-OS Agent 注册表。文件结构模式被用于技能目录的自动生成。 |
| **拒绝** | Tier 2-4 的 Agent 定义过于泛化（如"通用助手"），与 Molin-OS 已有的系统提示重复，未吸收。JSON-only 配置方式限制了动态行为注入，优先保留 .md 格式。 |
| **风险** | ⚠️ 项目星数中等（200+），维护频率下降。依赖设计可能被上游变化淘汰。建议每季度检查是否有新版更新。 |

#### Multi-Agent 教育系统（41★）

| 维度 | 内容 |
|------|------|
| **学到** | 5-Agent Mesh 架构的设计——不同于传统 Pipeline，Mesh 允许任意 Agent 间通信，特别适合学生建模需要多源数据的场景。BKT（贝叶斯知识追踪）+ SM-2（间隔重复）的混合算法是经典 + LLM 的实用折中方案。三语言实现（Python/LangGraph/Java Spring Boot/Go Gin）展示了架构的多语言适配性。 |
| **吸收** | Mesh 架构模式被纳入 Molin-OS 教育 Agent 管线设计文档。BKT 参数估计的 Python 实现片段被复用到学生模型模块。 |
| **拒绝** | 三语言实现本身过于冗余——Molin-OS 统一用 Python/TypeScript，Go/Java 版不吸收。SM-2 部分被 FSRS 替代（见下方 Anki 项目），不单独采用。 |
| **风险** | ⚠️ 41★ 较低，项目可能沉寂。但其架构价值已提取，即使项目不再更新也不影响已吸收部分。 |

#### FeeFee Companion（104★）

| 维度 | 内容 |
|------|------|
| **学到** | 三位一体（学生-教师-家长）K12 架构是 Molin-OS 教育 Agent 的最佳参考。五大学习法（费曼、SQ3R、PQ4R、康奈尔、思维导图）的工程化实现——不再是理论描述而是可执行的 Agent 路由逻辑。HERMES 反思引擎与 Molin-OS 同源，但其工程实现有独特的错误反馈循环设计。32 个功能模块的拆分解耦方式值得学习。 |
| **吸收** | 三位一体通信协议的消息格式被复用到 Molin-OS 多 Agent 通信层。五大学习法的路由逻辑被抽象为可配置的 skill 模板。32 个模块的目录结构被用作技能拆分参考。 |
| **拒绝** | 前端实现（React）与 Molin-OS 架构不匹配（统一接口层），不直接吸收。部分模块（如支付、排课）超出知识库管理范畴。 |
| **风险** | ✅ 工程成熟度最高的开源多 Agent 教育项目，活跃维护中。License（MIT）友好。 |

### 教育系统

#### EasyDS（31★）

| 维度 | 内容 |
|------|------|
| **学到** | 三层 Agent 架构（引导 Agent → 教学 Agent → 评价 Agent）实现费曼学习法的自动闭环——先教再评，形成"讲解→反馈→修正→强化"循环。这个闭环对学生主动学习场景的建模非常精准。 |
| **吸收** | 费曼闭环的 Agent 状态机逻辑被复用到 Molin-OS 的"教学-提问-纠正"skill 中。三层职责划分被用作 Agent 编排的参考。 |
| **拒绝** | 考研数据结构领域太窄，通用化改造后领域知识层几乎全部重写。项目规模小，代码风格不够统一，只取架构模式不取代码。 |
| **风险** | 🔴 31★，项目维护不活跃。作为架构参考已够用，不依赖其更新。 |

#### Flight School（28★）

| 维度 | 内容 |
|------|------|
| **学到** | Copilot SDK 驱动的自适应编程练习平台——Next.js 前端 + GitHub MCP 做代码提交管道 + 状态机管理学习进度。"not yet"增长心态评估哲学是一个出色的 prompt 设计模式——先肯定再改进，适合所有教育场景。 |
| **吸收** | "not yet"评估框架被吸收为 Molin-OS 评价 Agent 的默认 prompt 模板。GitHub MCP 集成模式被用作代码 skill 的参考架构。 |
| **拒绝** | Next.js 前端层不吸收（Molin-OS 统一接口）。Copilot SDK 绑定过紧，不适合通用化。 |
| **风险** | 🔴 28★，小众项目。但其"not yet"框架价值高，已独立提取。 |

### 内容创作与跨境

#### RedInk（5,200★）

| 维度 | 内容 |
|------|------|
| **学到** | 小红书图文自动生成的完整流水线——主题挖掘 → 文案生成 → 图片合成 → 排版发布。5,200★ 证明了其模式的可用性。图片合成中的模板系统和文案生成中的风格控制是关键技术点。 |
| **吸收** | 图文自动化流水线的主题-文案-视觉三段架构被纳入 Molin-OS 内容创作管线设计。模板系统的变量注入模式被复用。 |
| **拒绝** | 平台绑定（小红书特定格式）限制了通用性。直接代码复用意义不大，架构模式才是核心价值。 |
| **风险** | ✅ 5,200★，社区活跃，License 友好。但小红书平台政策变化可能影响项目方向。 |

#### 知识图谱项目（136★ + 65★）

| 维度 | 内容 |
|------|------|
| **学到** | K12 教育知识图谱全链路（Neo4j + TextCNN + Django）和百科数据源构建策略 + KNN 自动分类。两个项目的组合覆盖了从数据采集到图谱查询的完整链路。 |
| **吸收** | Neo4j 的图谱建模模式（实体-关系-属性三层）被吸收。百科数据爬取策略被复用到知识点采集管线。自动分类的 KNN 基线算法被纳入。 |
| **拒绝** | Django 后端过重，Molin-OS 用 FastAPI/Express 替代。TextCNN 分类模型已过时，被 Transformer-based 方案替代。 |
| **风险** | ⚠️ 两个项目星数中等，维护一般。技术栈（TextCNN）略老旧，但图谱建模部分仍有价值。 |

### 技术工具

#### Anki（28K★） + anki-mcp-server（277★） + py-fsrs（427★）

| 维度 | 内容 |
|------|------|
| **学到** | 间隔重复生态全貌——Anki 是最成功的间隔重复实践，anki-mcp-server 标准化了 AI 管理闪卡的协议，py-fsrs 提供了比 SM-2 更优的算法。FSRS 动态计算最优复习间隔，基于学生历史表现实时调整参数，解决了 SM-2 的固定间隔问题。MCP（Model Context Protocol）为 AI 工具集成提供了标准化接口。 |
| **吸收** | FSRS 算法已完全吸收为 Molin-OS 复习安排的核心算法。anki-mcp-server 的 MCP 协议实现被复用到 Molin-OS 工具集成层。Anki 的卡片模型（正面/反面/元数据）被用作闪卡 skill 的数据结构。 |
| **拒绝** | Anki 本身的桌面端代码（Qt/Python）过于庞大，不在吸收范围内。其同步服务器代码与 Molin-OS 架构不匹配。 |
| **风险** | ✅ Anki 28K★ 生态极其稳定。py-fsrs 和 anki-mcp-server 活跃维护中。License（AGPL）需要注意——Molin-OS 使用 FSRS 算法而非直接复制代码，无合规风险。 |

## 完整吸收周期演示：以 TheAgency 为例

追踪一个项目从发现到技能创建的完整过程：

```
Step 1: 发现 ──→ GitHub Trending / 社区推荐 → 发现 TheAgency（200+★）
Step 2: 评估 ──→ 扫描 README → 评估架构 → 决定 "MECE 框架 + Agent 定义" 有价值
Step 3: 研读 ──→ Frok 仓库 → 逐文件阅读 226 个 Agent 定义 → 理解 Tier 分级系统
Step 4: 吸收 ──→ 8 个 Tier 1 Agent 定义 → 转换为 SKILL.md 格式
                → 标签分类体系 → 复用到 Agent 注册表
                → 文件结构 → 应用于技能目录自动生成
Step 5: 拒绝 ──→ Tier 2-4 定义过于泛化 → 不吸收
                → JSON-only 配置方式 → 保留 .md 格式
Step 6: 技能 ──→ 新增 8 个 SKILL.md → 更新 Agent 注册表 → 更新技能目录生成器
Step 7: 记录 ──→ 写入本档案 → 标记风险 → 设置季度检查
```

**耗时**：从开始扫描到技能落地约 2 小时（Agent 自动执行）。如果人工操作，预估 2-3 天。

## 风险登记册

| 风险 | 影响项目 | 概率 | 影响 | 缓解措施 |
|------|----------|------|------|----------|
| **项目归档/停止维护** | TheAgency（200★）、EasyDS（31★） | 中 | 中 | 已提取架构价值；不依赖更新；季度检查 |
| **License 变更** | 所有 AGPL/LGPL 项目 | 低 | 高 | 仅吸收算法思想不直接复制代码；保留 License 审计 |
| **依赖冲突** | Anki 生态链（py-fsrs 更新可能 API 不兼容） | 中 | 中 | 锁定版本；封装适配层隔离变更 |
| **平台政策变动** | RedInk（小红书规则变化） | 中 | 低 | 仅用架构模式不绑定平台 |
| **技术栈过时** | 知识图谱项目（TextCNN 已被 Transformer 替代） | 高 | 低 | 仅吸收图谱建模部分；分类算法用 Molin-OS 自有方案 |
| **上游 API 变更** | Flight School（Copilot SDK 变动） | 中 | 低 | 仅用评估框架模式，不依赖 API |
| **社区分裂** | Anki 生态（不同实现方向冲突） | 低 | 中 | 追踪主流 fork，选用最活跃的实现 |

**风险评分公式**：`R = P × I`（Probability × Impact），评分 > 6 的需立即行动，4-6 的需监控，< 4 的接受。

## 扫描方法论

### 发现渠道

| 渠道 | 优先级 | 频率 | 用途 |
|------|--------|------|------|
| GitHub Trending（daily） | 高 | 每日 | 热点发现 |
| Awesome-XXX 聚合列表 | 中 | 每周 | 定向领域扫描 |
| HN / Reddit / Twitter AI 社区 | 中 | 每日 | 社区验证 |
| Paper-with-Code 关联仓库 | 低 | 每周 | 学术→工程转化 |
| 已有项目的 Dependencies/Similar | 中 | 按需 | 生态延伸 |

### 评估框架（E-A-D 三步）

1. **Evaluate（评估）**：5 维度评分卡（见决策记录）→ 得出总分
   - 总分 ≥ 80：深入研读 → 最多 4 小时
   - 总分 60-79：重点特征提取 → 最多 1 小时
   - 总分 < 60：brief 浏览 → 最多 15 分钟

2. **Absorb（吸收）**：源码研读 + 架构逆向
   - 读架构文档 → 读核心源码 → 跑 Demo → 读 Issue/PR 了解设计取舍
   - 输出：学到了什么 + 吸收什么 + 拒绝什么

3. **Document（记录）**：写入本档案
   - 更新项目记录 → 更新吸收度量 → 更新风险登记册
   - 触发新 skill 创建（如果适用）

### 周期性维护

- **每周**：扫描发现渠道，识别新项目候选
- **每月**：回顾本月新增项目，更新度量
- **每季度**：检查所有项目的风险状态，更新维护活跃度
- **每半年**：全档案审计，清理过期/已废弃的项目记录
