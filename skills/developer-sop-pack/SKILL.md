## 一、Lead SOP（开发需求获取）

### 需求来源

| 来源 | 方式 | 优先级 |
|------|------|--------|
| 直接指派 | Founder 对话中提出 | P0 |
| 系统优化 | 运维/财务系统触发（性能/成本优化） | P1 |
| Agent SOP 更新 | 其他 Agent 提出开发需求 | P1 |
| Bug/故障 | Escalation 触发 | P0（紧急）/ P2（常规） |

### 开发需求格式化

所有开发任务必须先格式化为：

```yaml
task_id: "DEV-20260517-001"
type: "feature / bugfix / refactor / optimization / infrastructure"
priority: "P0 / P1 / P2"
description: "做什么"
acceptance_criteria:
  - "条件1"
  - "条件2"
estimated_effort: "S/M/L/XL"
depends_on: []
context: "背景说明"
governance_level: "L0-auto / L1-notify / L2-approve"
```

## 二、Execution SOP（开发执行流程）

### 标准开发流水线

```
需求分析 → 技术方案 → 编码 → 测试 → 代码审查 → PR提交 → 部署
```

### Step 1: 需求分析
- 完全理解需求背景和目的
- 识别依赖项和前置条件
- 评估影响面（使用 codemap 或 gitnexus）
- 拆分任务（如果 > XL，必须拆分为多个子任务）

### Step 2: 技术方案
- P0/P1 任务必须写技术方案
- 方案包含：架构变更、接口设计、数据模型、风险点
- 方案经 Founder 确认（L2 审批）后才能开始编码

### Step 3: 编码
- 遵循项目编码规范
- 每次 PR 不超过 400 行变更
- 必须包含单元测试
- 写清楚注释（特别是不直观的逻辑）

### Step 4: 测试
- 单元测试覆盖率 ≥ 80%
- 集成测试覆盖关键路径
- 原有测试不能挂

### Step 5: 代码审查（吸收自 Agency Code Reviewer）

> 源：Agency Agents Code Reviewer · 吸收日期：2026-05-18

审查聚焦五个核心维度：**正确性 > 安全性 > 可维护性 > 性能 > 测试**。审查像导师，不是门卫——每条评论都应该教会点什么。

#### 优先级标记（强制使用）

| 标记 | 含义 | 说明 |
|------|------|------|
| 🔴 **Blocker** | 必须修复 | 安全漏洞、数据丢失风险、竞态条件、API 合约破坏、关键路径缺错误处理 |
| 🟡 **Suggestion** | 应该修复 | 缺输入验证、命名不清、缺重要测试、性能问题（N+1）、应提取的重复代码 |
| 💭 **Nit** | 锦上添花 | 风格不一致（如无 linter）、命名可改进、文档缺口、替代方案值得考虑 |

#### 审查清单

**🔴 Blocker 检查项**：
- 安全漏洞（注入、XSS、认证绕过）
- 数据丢失或损坏风险
- 竞态条件或死锁
- API 合约破坏
- 关键路径缺错误处理

**🟡 Suggestion 检查项**：
- 缺失输入验证
- 命名不清晰或逻辑混乱
- 重要行为缺测试
- 性能问题（N+1 查询、不必要的分配）
- 应提取的重复代码

**💭 Nit 检查项**：
- linter 未覆盖的风格不一致
- 命名小幅改进
- 文档缺口
- 值得考虑的替代方案

#### 审查评论格式

```
🔴 **安全：SQL 注入风险**
第 42 行：用户输入直接拼接到查询字符串中。

**原因**：攻击者可通过 name 参数注入 `'; DROP TABLE users; --`。

**建议**：
- 改用参数化查询：`db.query('SELECT * FROM users WHERE name = $1', [name])`
```

#### 审查沟通规范
- 开头先总结：整体印象、关键关切、做得好的地方
- 持续使用优先级标记
- 意图不明时先提问，不假设错误
- 结尾附鼓励和下一步
- 一次审查给完整反馈，不分批追加
- PR 必须有清晰描述，必须通过 CI 检查

### Step 6: PR 提交
- 分支命名：`{type}/{short-description}`
- PR 描述包含：做了什么、怎么测的、影响面
- P0 任务 PR 附加 urgent 标签

## 三、QA SOP（代码质量质检）

| 维度 | 权重 | 检查项 |
|------|------|--------|
| 功能正确性 | 30% | 是否满足需求/AC 全部通过 |
| 代码质量 | 20% | 可读性、注释、命名规范 |
| 测试覆盖 | 20% | 覆盖率 ≥ 80%、测试有意义 |
| 性能安全 | 15% | 无性能退化、无安全漏洞 |
| 架构一致性 | 15% | 是否符合项目架构约定 |

### 否决条件
- 测试挂掉
- 引入安全漏洞
- 直接修改 main/master 分支

## 四、Escalation SOP

| 场景 | 触发 | 动作 |
|------|------|------|
| P0 Bug | 生产环境故障 | 立即修复 + L1 通知 |
| 技术方案需决策 | 有重大 trade-off | 暂停，等待 Founder 决策 |
| 开发阻塞 | 依赖其他系统不可用 | L1 通知 + 寻找替代方案 |
| 合并冲突 | 冲突无法自动解决 | 标记需要人工介入 |

## 六、API 测试 SOP（吸收自 Agency API Tester）

> 源：Agency Agents API Tester · 吸收日期：2026-05-18

### API 测试策略

**三大支柱**：
1. **功能测试** — 端点和功能正确性
2. **安全测试** — OWASP API Security Top 10
3. **性能测试** — 负载、压力、SLA 验证

**强制要求**：每个 API 必须通过功能、安全和性能验证。

### 安全测试要点

- 始终彻底测试认证和授权机制
- 验证输入净化和 SQL 注入防护
- 测试常见 API 漏洞（OWASP API Security Top 10）
- 验证数据加密和安全传输
- 测试速率限制和滥用防护

### 性能 SLA

| 指标 | 目标 |
|------|------|
| 95分位响应时间 | < 200ms |
| 负载测试容量 | ≥ 10x 正常流量 |
| 正常负载错误率 | < 0.1% |
| 测试套执行时间 | < 15 分钟 |

### API 测试工作流

1. **API 发现与分析**：编目所有内外 API，评估当前覆盖度
2. **测试策略设计**：功能 + 安全 + 性能全面覆盖
3. **测试自动化**：Playwright / k6 / REST Assured 构建自动化套件
4. **CI/CD 集成**：测试加入流水线，设置质量门禁
5. **生产监控**：健康检查 + 告警

### API 测试报告模板

```markdown
# [API 名称] 测试报告

## 🔍 测试覆盖分析
**功能覆盖**：[端点覆盖率 > 95% 及详细分解]
**安全覆盖**：[认证、授权、输入验证结果]
**性能覆盖**：[负载测试结果及 SLA 达标情况]

## ⚡ 性能测试结果
**响应时间**：[95分位 < 200ms 目标达成情况]
**吞吐量**：[各负载条件下的请求/秒]
**可扩展性**：[10x 正常负载下性能]

## 🔒 安全评估
**认证**：[Token 验证、会话管理]
**授权**：[RBAC 验证]
**输入验证**：[SQLi、XSS 防护]

## 🚨 问题与建议
**Critical**：[P1 安全和性能]
**性能瓶颈**：[识别及解决方案]
**安全漏洞**：[风险评估及缓解]
```

### API 测试成功指标

- 所有端点测试覆盖率 ≥ 95%
- 零 Critical 安全漏洞进入生产
- API 性能持续满足 SLA
- 90% API 测试自动化并集成 CI/CD
- 完整测试套执行 < 15 分钟
