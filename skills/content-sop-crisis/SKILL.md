# 内容 Agent Crisis SOP（危机处理）

## 定位

Crisis SOP 解决的问题：

> 系统没有"崩溃模式"时，崩溃就是灾难。
> 有 Crisis SOP 时，崩溃只是一次预定排练。

---

## 一、风险场景矩阵

### 外部依赖故障

| 风险场景 | 可能性 | 影响面 | 恢复策略 | 自动/手动 |
|----------|--------|--------|----------|-----------|
| DeepSeek API 不可用 | 中 | 所有内容生产 | 切换备选 Provider（OpenRouter / 直接 API） | 自动 |
| 小红书 API 封禁 | 中 | 分发阻断 | 切换备用账号 / 降级为手动发布 | 半自动 |
| OpenAI API 异常 | 低 | 视觉/Chat 任务 | 降级到 DeepSeek / 通义千问 | 自动 |
| web_search 不可用 | 中 | Intel 情报采集 | 降级为本地缓存数据 + 陈旧标记 | 自动 |
| Obsidian 同步失败 | 低 | 产出存档 | 本地缓存 + 恢复后重同步 | 自动 |
| 飞书 Webhook 失效 | 低 | 告警通道 | 降级为邮件通知 | 自动 |

### 运营风险

| 风险场景 | 可能性 | 影响面 | 处理策略 |
|----------|--------|--------|----------|
| 内容违规 | 低 | 品牌声誉 | 自动撤回 + 人工审查 |
| Token 成本失控 | 中 | 预算超支 | 降级模型 + 暂停非核心任务 |
| 飞轮级联断裂 | 低 | 全线停摆 | 级联告警 + 紧急修复 |
| 数据幻觉传播 | 中 | 内容质量下降 | Gatekeeper 拦截 + 修正重发 |

## 二、降级策略（Fallback Chain）

### 模型降级链

```
DeepSeek pro（主）
    ↓ 不可用时
DeepSeek flash（备1：降级为快速轻量模式）
    ↓ 仍不可用时
OpenRouter 回退（备2：自动切换路由）
    ↓ 仍不可用时
本地缓存响应（紧急模式：返回预设响应模板）
```

### 情报采集降级链

```
实时 web_search
    ↓ 不可用时
读取 relay/ 最新缓存（带陈旧标记.markdown_stale）
    ↓ 缓存也不存在时
使用 last_30_days 等本地数据源
    ↓ 全部不可用时
跳过情报采集，标记为"情报缺失"
```

### 分发降级链

```
API 发布
    ↓ 失败时
重试 2 次（间隔 30 秒）
    ↓ 仍失败
降级为"待发布" → 写入 Obsidian 待处理区
    ↓ 持续失败（>1天）
飞书通知人工处理
```

## 三、告警与通知

### 告警级别

| 级别 | 颜色 | 含义 | 通知方式 | 响应时间 |
|------|------|------|----------|----------|
| L0 信息 | 绿 | 无事，例行记录 | 记日志 | - |
| L1 警告 | 黄 | 单次故障已自动恢复 | 复盘时汇总 | 次日 |
| L2 异常 | 橙 | 持续故障，已降级 | 飞书通知 | 1小时 |
| L3 严重 | 红 | 系统级故障，飞轮停摆 | 飞书 + 邮件 | 立即 |
| L4 灾难 | 紫 | 数据丢失/安全问题 | 全部通道 | 立即 |

### 告警格式

```
[CRISIS:L{n}] {场景名称}
━━━━━━━━━━━━━━━
时间：{datetime}
影响面：{affected_components}
状态：{降级策略描述}
预计恢复：{估计时间 / 待定}

当前动作：{已执行的动作}
建议动作：{建议人工操作}
━━━━━━━━━━━━━━━
```

## 四、恢复流程

### 自动恢复检查

每 15 分钟自动检查已降级组件的状态：

```
1. 尝试重连故障组件
2. 如果成功 → 从降级状态恢复
3. 如果仍失败 → 继续降级，升级告警级别
4. 如果连续 3 次检查失败 → 升级到 L3，触发人工介入
```

### 恢复后动作

```
1. 切回主链路
2. 清理降级期间的临时数据（如缓存标记）
3. 在复盘笔记中记录事件
4. 如有 SOP 缺口 → 更新 Crisis SOP
```

## 五、集成方式

### 在 Content SOP 中引用

Crisis SOP 不作为独立 Cron 运行，而是**注入到所有执行 SOP 和 Cron 的 fallback 逻辑中**。

各 Execution SOP 的最后一步都应有：

```
exception_handler: 调用 content-sop-crisis 的对应降级策略
```

### 在 Cron 中引用

每周日增长复盘增加 Crisis 检查项：

```
- 过去一周有没有触发 Crisis？
- 平均恢复时间？
- 是否有可以优化的降级策略？
```

## 七、预演计划

建议每月第一个周日进行一次 Crisis 预演：

```
1. 手动模拟一个故障场景（如关闭 API 访问）
2. 观察系统自动降级
3. 记录恢复时间
4. 更新 Crisis SOP 中的空白点
```
